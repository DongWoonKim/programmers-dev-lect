# 회원 관리 프로그램 만들기 (인터페이스 · 위임)

> 같은 회원 관리 프로그램을, 이번에는 **저장 방법을 갈아끼울 수 있게** 만듭니다. `interface` 로 "저장소가 갖춰야 할 규약"을 정하고, 그 규약을 지키는 구현을 **두 개** 만듭니다. 화면 담당(`MemberApp`)은 배열인지 무엇인지 **끝까지 모른 채** 동작합니다. **아래 Step을 순서대로 따라가면, 마지막 Step에서 프로그램이 완성됩니다.**
>
> **선행 과제**: `회원관리만들기(배열)` / `회원관리만들기(추상클래스)`

---

## 1. 무엇을 만드나요?

기능은 지금까지와 같습니다. 달라진 것은 시작할 때 **어떤 저장소가 꽂혔는지** 보여주고, 저장·삭제 때마다 **로그가 찍힌다**는 점입니다.

```
[요금제를 선택하세요]
[1]Lite : 10명 [2]Basic : 20명 [3]Premium : 30명
> 1

저장소: 배열 저장소(정원 10명) + 로그

[수행할 업무를 선택하세요 - 현재 회원수 : 0명]
[1]회원추가 [2]회원조회(메일) [3]회원조회(이름)
[4]회원전체조회 [5]회원정보 수정 [6]회원삭제
[7]프로그램 종료
> 1

이름을 입력하세요.
> 홍길동
이메일을 입력하세요.
> hong@a.com
연락처를 입력하세요.
> 010-1111-1111
  [LOG] add(hong@a.com) -> true
회원이 등록되었습니다.
```

같은 이메일을 또 넣으면:

```
  [LOG] add(hong@a.com) -> false
이미 존재하는 회원입니다.
```

그리고 **`Main.kt` 의 한 줄만 바꾸면** 로그가 통째로 사라집니다. `MemberApp` 은 한 글자도 안 고칩니다.

```kotlin
val storage: MemberStorage = LoggingMemberStorage(ArrayMemberStorage(planNo))   // 로그 있음
val storage: MemberStorage = ArrayMemberStorage(planNo)                          // 로그 없음
```

**이 "한 줄만 바꾸면 되는 상태"를 만드는 것이 이 과제의 전부입니다.**

|번호|기능|설명|
|---|---|---|
|0|요금제 선택|Lite(10) / Basic(20) / Premium(30) → 정원 결정|

## 3. 학습 목표

|개념|어디서 쓰나|
|---|---|
|`interface`|`MemberStorage` — 상태 없이 규약만 정한다|
|인터페이스 프로퍼티|`val memberCnt: Int` — 자바 인터페이스에는 없던 기능|
|기본 구현 메서드|`fun isEmpty() = memberCnt == 0` — 구현체가 안 만들어도 쓸 수 있다|
|구현과 `override`|`class ArrayMemberStorage : MemberStorage`|
|`val` 을 `var` 로 재정의|`override var memberCnt` — 넓히는 것은 되고 좁히는 것은 안 된다|
|**규약에 의존하기**|`MemberApp(private val storage: MemberStorage)` ⭐|
|위임 (`by`)|`LoggingMemberStorage(origin) : MemberStorage by origin`|
|감싸기(래핑)|기존 구현을 고치지 않고 기능을 덧붙인다|
|인터페이스 설계|무엇이 본질이고 무엇이 구현의 사정인가 가르기|
|추상 클래스 vs 인터페이스|언제 무엇을 쓰는가|

## 4. 핵심 개념

### (1) 문제 — `MemberApp` 이 구현에 묶여 있다

추상 클래스 버전에서 `MemberApp` 은 이렇게 생겼습니다.

```kotlin
class MemberApp(private val manager: MemberManager) { ... }
```

`MemberManager` 는 **배열에 저장하는 구체적인 클래스**입니다. 그래서 "파일에 저장하자", "저장할 때 로그를 남기자"가 되는 순간 `MemberApp` 까지 고쳐야 합니다.

그 사이에 **규약**을 하나 끼워 넣습니다.

```
[before]  MemberApp ──────────> MemberManager              (구현에 직접 묶임)

[after]   MemberApp ──> MemberStorage <── ArrayMemberStorage
                          (규약)      <── LoggingMemberStorage
                                      <── (나중에 FileMemberStorage 도)
```

`MemberApp` 은 **"회원을 넣고 찾고 지울 수 있는 무언가"** 만 알면 됩니다. 그것이 배열인지 파일인지는 알 필요도 없고, 알아서도 안 됩니다.

### (2) 인터페이스 문법 — 자바와 다른 점

```kotlin
interface MemberStorage {
    val memberCnt: Int                  // 프로퍼티를 선언할 수 있다 (자바는 상수만 가능)
    fun add(member: Member): Boolean    // 본문 없음 → 구현하는 쪽이 채운다

    fun isEmpty(): Boolean {            // 본문이 있는 메서드도 된다 (자바 8 default 메서드)
        return memberCnt == 0
    }
}

class ArrayMemberStorage : MemberStorage {      // implements 자리에도 콜론(:)
    override val memberCnt: Int = 0             // override 는 생략할 수 없다
    override fun add(member: Member): Boolean { ... }
}
```

- 상속(`extends`)과 구현(`implements`)을 **콜론 하나**로 씁니다.
- `override` 는 **문법**입니다. 자바의 `@Override` 는 붙여도 그만인 주석이었지만, 코틀린은 빠지면 컴파일 에러입니다.
- 인터페이스는 **상태를 저장할 수 없습니다.** 프로퍼티에 초깃값을 줄 수 없고 getter 만 만들 수 있습니다.

### (3) ⭐ 인터페이스 설계 — 무엇을 넣고 무엇을 뺄까

`MemberManager` 에는 `totalCnt`(정원)가 있었습니다. **이것을 규약에 넣어야 할까요?**

|후보|넣을까?|이유|
|---|---|---|
|`add` / `delete` / `find...`|✅ 넣는다|저장소라면 당연히 할 수 있어야 하는 일|
|`memberCnt`|✅ 넣는다|몇 명인지는 어느 저장소든 답할 수 있다|
|`isFull`|✅ 넣는다|"더 넣을 수 있는가"는 저장소마다 답이 다를 뿐, 질문 자체는 공통|
|`totalCnt` (정원)|❌ 뺀다|**크기가 고정된 배열을 쓰기 때문에 생긴 사정.** DB 저장소에는 정원이 없다|
|`findIndex`|❌ 뺀다|배열이라서 인덱스가 있는 것. 파일 저장소에 인덱스는 무의미하다|

> 💡 **이렇게 "무엇이 본질이고 무엇이 구현의 사정인가"를 가르는 것이 인터페이스 설계입니다.**
> 규약에 구현의 사정이 섞여 들어가면, 그 규약은 다른 구현을 받아들이지 못합니다.

정원을 뺀 대가도 있습니다. 메뉴의 `현재 회원수 : 3/10` 이 `현재 회원수 : 3명` 으로 바뀝니다. 무엇을 얻고 무엇을 잃을지 판단하는 것까지가 설계입니다. (도전 과제 4번)

### (4) 위임 (`by`) — 감싸서 기능 덧붙이기

`LoggingMemberStorage` 는 **회원을 직접 저장하지 않습니다.** 진짜 저장소에게 그대로 넘기고, 오가는 길목에서 로그만 찍습니다.

```
MemberApp ──> LoggingMemberStorage ──> ArrayMemberStorage
                   (로그만 찍는다)         (실제로 저장한다)
```

```kotlin
class LoggingMemberStorage(private val origin: MemberStorage) : MemberStorage by origin {

    override fun add(member: Member): Boolean {
        val result = origin.add(member)          // 실제 저장은 원래 저장소가 한다
        println("  [LOG] add(${member.email}) -> $result")
        return result
    }
}
```

`by origin` 이 위임입니다. **내가 직접 만들지 않은 멤버는 전부 `origin` 에게 자동으로 넘깁니다.** `findByEmail`, `findByName`, `getAll`, `memberCnt`, `isFull`, `isEmpty()` 를 한 줄도 쓰지 않았는데 그대로 동작합니다.

> 💡 위임이 없었다면 이 6개를 **전부 손으로 옮겨 적어야** 했습니다. 그리고 인터페이스에 메서드가 하나 추가될 때마다 또 옮겨 적어야 했겠죠.

이런 구조가 가능한 이유는 **`LoggingMemberStorage` 도, 그 안의 `ArrayMemberStorage` 도 똑같이 `MemberStorage` 이기 때문**입니다.

### (5) 추상 클래스와 인터페이스, 언제 무엇을?

|기준|추상 클래스|인터페이스|
|---|---|---|
|개수|하나만 상속|여러 개 구현 가능|
|생성자|있다|**없다**|
|상태(값) 저장|가능|불가 (getter 만)|
|의미|"~는 ~이다" (is-a)|"~는 ~을 할 수 있다" (can-do)|

이 두 과제를 나란히 놓고 보세요.

- **회원(`Member`)** 은 이름·이메일·연락처라는 공통 **상태**를 물려줘야 합니다. 인터페이스는 생성자가 없어서 이걸 못 합니다. → **추상 클래스**
- **저장소(`MemberStorage`)** 는 물려줄 상태가 없습니다. 필요한 건 "이런 기능을 갖춰라"뿐입니다. → **인터페이스**

그리고 인터페이스였기 때문에 `LoggingMemberStorage` 같은 **감싸는 구현**을 만들 수 있었습니다.

## 5. 파일 구조

```
src/main/kotlin/member_interface/
├── Member.kt                  회원 한 명
├── MemberStorage.kt           규약 (interface)
├── ArrayMemberStorage.kt      구현 1) 배열에 저장
├── LoggingMemberStorage.kt    구현 2) 감싸서 로그 남기기
├── MemberApp.kt               메뉴와 입력, 출력 (규약에만 의존)
└── Main.kt                    어느 구현을 쓸지 정하는 곳
```

|파일|역할|
|---|---|
|`Member`|이름·이메일·연락처 + `toString()`|
|`MemberStorage`|저장소가 갖춰야 할 규약. **구현이 없다**|
|`ArrayMemberStorage`|배열 + 정원. 실제로 저장하는 곳|
|`LoggingMemberStorage`|다른 저장소를 감싸 로그만 추가|
|`MemberApp`|`MemberStorage` 타입만 알고 동작|
|`Main`|**구현을 고르는 유일한 곳**|

> 💡 `Main.kt` 가 특별한 이유: 프로그램 전체에서 **"어느 구현을 쓸지" 아는 곳은 여기 한 곳뿐**입니다. 나머지 파일은 전부 규약만 압니다. 이런 구조를 만드는 것이 목표입니다.

## 6. Step by Step

---

### Step 1. 회원 클래스 (`Member.kt`)

**목표**: 회원 한 명을 표현한다. (추상 클래스 버전과 달리 등급은 없다)

**힌트**

```kotlin
package member_interface

class Member(var name: String, var email: String, var phone: String) {

    override fun toString(): String {
        return "[이름] $name, [이메일] $email, [연락처] $phone"
    }
}
```

> 이번 과제에서 바뀌는 것은 **"회원을 어디에 어떻게 저장하는가"** 이지 회원 자체가 아닙니다.

**확인**: 컴파일 성공.

---

### Step 2. ⭐ 규약 만들기 (`MemberStorage.kt`)

**목표**: 저장소가 갖춰야 할 것만 골라 인터페이스로 선언한다.

**할 일**

1. `interface MemberStorage` 를 만든다.
2. 프로퍼티 3개를 선언한다: `storageName`, `memberCnt`, `isFull`.
3. 메서드 5개를 선언한다: `add`, `findByEmail`, `findByName`, `delete`, `getAll`.
4. `isEmpty()` 는 **기본 구현**으로 만든다.
5. **`totalCnt` 와 `findIndex` 는 넣지 않는다.** 왜 그런지 4-(3)을 다시 읽어 보세요.

**힌트**

```kotlin
package member_interface

interface MemberStorage {

    val storageName: String     // 화면에 보여 줄 저장소 이름
    val memberCnt: Int          // 현재 회원 수
    val isFull: Boolean         // 더 넣을 수 있는가

    fun add(member: Member): Boolean
    fun findByEmail(email: String): Member?
    fun findByName(name: String): Member?
    fun delete(email: String): Boolean
    fun getAll(): Array<Member>

    // 기본 구현. memberCnt 만 있으면 어느 저장소든 똑같이 계산된다.
    fun isEmpty(): Boolean {
        return memberCnt == 0
    }
}
```

> 프로퍼티에 **값이 없습니다.** 인터페이스는 상태를 저장할 수 없고, 구현하는 쪽이 채웁니다.
> `isEmpty()` 를 여기 둔 덕분에 구현 클래스가 10개로 늘어도 **이 메서드는 한 번만 작성된 것**입니다.
> 이 파일에는 `Array` 도 `null` 도 나오지 않습니다. **"어떻게"가 아니라 "무엇을"만 적혀 있는지** 확인하세요.

**확인**: 컴파일 성공. 이 파일만 읽고도 "저장소가 무슨 일을 할 수 있는지" 알 수 있으면 잘 만든 것입니다.

---

### Step 3. 배열 저장소 (1) — 프로퍼티와 검색

**목표**: `MemberStorage` 를 구현하는 배열 저장소의 뼈대를 만든다.

**할 일**

1. `class ArrayMemberStorage(planNo: Int) : MemberStorage`
2. `totalCnt` 와 `members` 는 **규약에 없으므로 `private`** 으로 감춘다.
3. `memberCnt` 를 `override var` + `private set` 으로 만든다.
4. `storageName`, `isFull` 을 구현한다.
5. `findIndex` 는 규약에 없는 `private` 함수로 만든다.

**힌트**

```kotlin
class ArrayMemberStorage(planNo: Int) : MemberStorage {

    private val totalCnt = planNo * 10
    private val members = Array(totalCnt) { Member("", "", "") }

    override var memberCnt = 0
        private set

    override val storageName = "배열 저장소(정원 ${totalCnt}명)"

    override val isFull: Boolean
        get() = memberCnt == totalCnt

    private fun findIndex(email: String): Int {
        for (i in 0 until memberCnt) {
            if (members[i].email == email) return i
        }
        return -1
    }
}
```

> ⭐ **규약에서는 `val memberCnt` 였는데 여기서는 `var` 로 재정의했습니다.** 읽기만 하겠다고 약속한 것을 **읽고 쓸 수 있게 넓히는 것은 허용**됩니다. (그 반대는 안 됩니다) `private set` 이라 밖에서는 여전히 읽기 전용입니다.
> `isFull` 의 판단 기준을 **구현이 정합니다.** 이 저장소에서 '꽉 찼다'는 정원을 다 채웠다는 뜻입니다.
> `findIndex` 는 규약에 없습니다. **인터페이스는 밖에 보여 줄 것만 정하지, 안에서 무엇을 만들어 쓰든 상관하지 않습니다.**
> 회원이 추상 클래스가 아니므로 빈 칸을 `Member("", "", "")` 로 채울 수 있습니다. `null` 처리가 필요 없습니다.

**확인**: 아직 메서드를 다 구현하지 않아 컴파일 에러가 납니다. **에러 메시지를 읽어 보세요.** "Class is not abstract and does not implement abstract member" — 이것이 인터페이스가 강제하는 힘입니다.

---

### Step 4. 배열 저장소 (2) — 추가 · 조회 · 삭제

**목표**: 규약의 나머지를 전부 구현해 컴파일을 통과시킨다.

**할 일**: `add`, `findByEmail`, `findByName`, `delete`, `getAll` 을 `override` 로 구현한다.

**힌트**

```kotlin
    override fun add(member: Member): Boolean {
        if (isFull) return false
        if (findIndex(member.email) != -1) return false

        members[memberCnt] = member
        memberCnt++
        return true
    }

    override fun findByEmail(email: String): Member? {
        val idx = findIndex(email)
        return if (idx == -1) null else members[idx]
    }

    override fun findByName(name: String): Member? {
        for (i in 0 until memberCnt) {
            if (members[i].name == name) return members[i]
        }
        return null
    }

    override fun delete(email: String): Boolean {
        val idx = findIndex(email)
        if (idx == -1) return false

        for (i in idx until memberCnt - 1) {
            members[i] = members[i + 1]      // 당기기
        }

        memberCnt--
        members[memberCnt] = Member("", "", "")   // 꼬리 정리
        return true
    }

    override fun getAll(): Array<Member> {
        return members.copyOfRange(0, memberCnt)  // 복사본을 넘긴다
    }

    // isEmpty() 는 재정의하지 않는다. 인터페이스의 기본 구현을 그대로 쓴다.
```

> 알맹이는 지금까지 만든 것과 **똑같습니다.** 달라진 건 `: MemberStorage` 가 붙었고 멤버마다 `override` 가 붙었다는 것뿐입니다.
> `getAll()` 이 `members` 를 그대로 넘기지 않는 이유: 밖에서 `members[0] = ...` 로 저장소를 직접 갈아 끼울 수 있기 때문입니다.
> `isEmpty()` 를 만들지 않아도 컴파일이 되는 것을 확인하세요. **기본 구현이 있는 멤버는 구현 의무가 없습니다.**

**확인**: 컴파일 성공. `override` 를 하나 지워 보고 어떤 에러가 나는지도 확인해 보세요.

### Step 5. ⭐ 화면 담당 — 규약에만 의존하기 (`MemberApp.kt`)

**목표**: `MemberApp` 이 **구현 클래스 이름을 한 번도 쓰지 않도록** 만든다.

**할 일**

1. 생성자 매개변수의 자료형을 **`MemberStorage`** 로 한다. (`ArrayMemberStorage` 가 아니다!)
2. `start()` 시작 시 `storage.storageName` 을 출력한다.
3. 메뉴·추가·조회·수정·삭제를 만든다. 정원이 없으므로 `현재 회원수 : N명` 으로 표시한다.

**힌트**

```kotlin
class MemberApp(private val storage: MemberStorage) {      // ⭐ 규약 타입

    fun start() {
        println("\n저장소: ${storage.storageName}")        // 어떤 구현이 꽂혔는지 확인용

        while (true) {
            when (printMenu()) {
                1 -> addMember()
                2 -> selectByEmail()
                3 -> selectByName()
                4 -> selectAll()
                5 -> updateMember()
                6 -> deleteMember()
                7 -> {
                    println("이용해주셔서 감사합니다.")
                    return
                }
                else -> println("올바른 번호를 입력하세요.")
            }
        }
    }

    private fun printMenu(): Int {
        // 정원(totalCnt)은 규약에 없으므로 물어볼 수 없다
        println("\n[수행할 업무를 선택하세요 - 현재 회원수 : ${storage.memberCnt}명]")
        println("[1]회원추가 [2]회원조회(메일) [3]회원조회(이름)")
        println("[4]회원전체조회 [5]회원정보 수정 [6]회원삭제")
        println("[7]프로그램 종료")
        print("> ")
        return readln().toIntOrNull() ?: -1
    }

    private fun addMember() {
        if (storage.isFull) {
            println("회원이 꽉 찼습니다.")
            return
        }

        println("이름을 입력하세요.")
        val name = readln()
        println("이메일을 입력하세요.")
        val email = readln()
        println("연락처를 입력하세요.")
        val phone = readln()

        if (storage.add(Member(name, email, phone))) {
            println("회원이 등록되었습니다.")
        } else {
            println("이미 존재하는 회원입니다.")
        }
    }

    private fun selectAll() {
        if (storage.isEmpty()) {          // 인터페이스의 기본 구현을 부른다
            println("등록된 회원이 없습니다.")
            return
        }

        val all = storage.getAll()
        for (i in all.indices) {
            println("${i + 1}. ${all[i]}")
        }
    }

    // selectByEmail / selectByName / updateMember / deleteMember 는
    // 추상 클래스 버전과 같습니다. manager 를 storage 로 바꾸면 됩니다.
}
```

> ⭐ **딱 한 단어 차이입니다.** `MemberManager` → `MemberStorage`. 이 한 단어 덕분에 이 파일은 저장 방식이 바뀌어도 **영원히 고칠 일이 없습니다.**
> `storage.isEmpty()` 를 주목하세요. `ArrayMemberStorage` 는 이 메서드를 만든 적이 없는데 호출됩니다.
> 이 파일에서 `ArrayMemberStorage` 라는 단어를 검색해 보세요. **한 번도 안 나와야 정답입니다.**

**확인**: 컴파일 성공.

### Step 6. 조립하고 한 번 돌려보기 (`Main.kt`)

**목표**: 여기까지로 프로그램이 완전히 동작하는지 확인한다. (로그는 아직 없다)

**힌트**

```kotlin
package member_interface

private fun printPricePlan(): Int {
    println("[요금제를 선택하세요]")
    println("[1]Lite : 10명 [2]Basic : 20명 [3]Premium : 30명")
    print("> ")
    return readln().toIntOrNull() ?: 1
}

fun main() {
    val planNo = printPricePlan()

    val storage: MemberStorage = ArrayMemberStorage(planNo)   // ⭐ 구현을 고르는 유일한 곳

}
```

> 변수의 자료형을 **`MemberStorage` 로 적어 두는 것**이 중요합니다. 이러면 오른쪽을 무엇으로 바꿔도 아래 코드는 그대로입니다.

**확인**: 추가·조회·수정·삭제가 모두 되면 성공. `저장소: 배열 저장소(정원 10명)` 이 나오는지도 확인하세요.

### Step 7. ⭐ 감싸는 저장소 만들기 (`LoggingMemberStorage.kt`)

**목표**: 기존 저장소를 **한 글자도 고치지 않고** 로그 기능을 덧붙인다.

**할 일**

1. 생성자로 다른 `MemberStorage` 를 받는다.
2. `: MemberStorage by origin` 으로 위임한다.
3. `storageName`, `add`, `delete` **세 개만** 재정의한다.

**힌트**

```kotlin
package member_interface

class LoggingMemberStorage(private val origin: MemberStorage) : MemberStorage by origin {

    override val storageName = "${origin.storageName} + 로그"

    override fun add(member: Member): Boolean {
        val result = origin.add(member)      // 실제 저장은 원래 저장소가 한다
        println("  [LOG] add(${member.email}) -> $result")
        return result
    }

    override fun delete(email: String): Boolean {
        val result = origin.delete(email)
        println("  [LOG] delete($email) -> $result")
        return result
    }
}
```

> **인터페이스 멤버가 9개인데 3개만 썼습니다.** 나머지 6개(`findByEmail`, `findByName`, `getAll`, `memberCnt`, `isFull`, `isEmpty`)는 `by origin` 이 자동으로 넘겨줍니다.
> `by` 를 지워 보세요. **6개를 전부 구현하라는 에러**가 쏟아집니다. 위임이 무엇을 대신해 줬는지 눈으로 확인할 수 있습니다.
> 이 클래스는 배열도 모르고 정원도 모릅니다. **`MemberStorage` 라는 것만 알면 무엇이든 감쌀 수 있습니다.**

**확인**: 컴파일 성공.

**할 일**: `Main.kt` 의 `storage` 한 줄을 바꾼다. **다른 파일은 절대 건드리지 않는다.**

## 7. 세 버전 비교

|                |배열 버전|추상 클래스 버전|인터페이스 버전|
|---|---|---|---|
|나누는 기준|나누지 않음|**데이터**가 여러 종류|**기능의 구현**이 여러 개|
|핵심 문법|최상위 함수 · 배열|`abstract class` · 다형성|`interface` · `by` 위임|
|무엇이 쉬워지나|—|**등급 추가**가 쉬워진다|**저장 방식 교체**가 쉬워진다|
|회원 표현|`Array<String>` 3칸|`Member` 3형제|`Member` 하나|
|`MemberApp` 이 아는 것|—|`MemberManager` (구현)|`MemberStorage` (규약)|
|추가 비용|—|`Array<Member?>` null 처리|정원 표시를 잃음|

> **둘 중 뭐가 더 좋은가?** 그런 건 없습니다. **무엇이 여러 개가 될 것 같은가**로 고릅니다.
> 회원 등급이 늘어날 것 같으면 추상 클래스로, 저장 방식이 바뀔 것 같으면 인터페이스로 나눕니다. 둘 다면 둘 다 씁니다.

## 8. 최종 완성 체크리스트

- [ ] `interface MemberStorage` — 프로퍼티 3개 + 메서드 5개 + 기본 구현 1개
- [ ] 인터페이스에 `totalCnt` / `findIndex` 같은 **구현의 사정이 섞이지 않았다**
- [ ] `ArrayMemberStorage` 가 규약을 전부 구현하고, 내부 사정은 `private` 으로 감췄다
- [ ] `override var memberCnt ... private set` — `val` 을 `var` 로 넓혀 재정의
- [ ] `MemberApp` 의 생성자 자료형이 `MemberStorage` 다 ⭐
- [ ] `MemberApp` 안에 구현 클래스 이름이 한 번도 안 나온다 ⭐
- [ ] `LoggingMemberStorage` 가 `by origin` 으로 위임하고 3개만 재정의
- [ ] `Main.kt` 한 줄로 구현을 교체할 수 있다
- [ ] `isEmpty()` 를 구현체가 만들지 않았는데 동작한다

## 9. 개선 & 도전 과제

**확장 도전 과제**

1. **아무것도 저장하지 않는 저장소** ⭐ — `EmptyMemberStorage` 를 만들어 보세요. `add` 는 항상 `false`, `getAll` 은 빈 배열(`arrayOf()`), `memberCnt` 는 항상 0을 돌려주면 됩니다.
   `Main.kt` 한 줄만 바꿔 꽂아 보세요. **`MemberApp` 이 정말 안 고쳐지는지 확인하는 것이 이 과제의 핵심입니다.**
2. **두 겹으로 감싸기** — `LoggingMemberStorage(LoggingMemberStorage(ArrayMemberStorage(2)))` 를 실행하면 어떻게 될까요? 왜 그런지 설명해 보세요.
3. **조회에도 로그 남기기** — `findByEmail` 을 `override` 해서 `origin.findByEmail(...)` 결과를 찍어 보세요. **필요한 것만 골라 덮어쓸 수 있다**는 위임의 장점을 확인할 수 있습니다.
4. **잃어버린 정원 되찾기** — 메뉴에 `3/10` 을 다시 표시하려면?
   - (a) `MemberStorage` 에 `val capacity: Int` 를 추가한다 → 정원이 없는 저장소는 무엇을 돌려줄까? (`-1`? `Int.MAX_VALUE`?)
   - (b) `MemberApp` 에서 `if (storage is ArrayMemberStorage)` 로 확인한다 → 규약에 의존한다는 원칙이 깨진다
   - **정답이 하나가 아닙니다.** 무엇을 잃고 무엇을 얻을지 직접 판단해 보세요. 이 고민 자체가 설계입니다.
5. **통계 저장소** — 저장/삭제 횟수를 세는 `CountingMemberStorage` 를 만들어 보세요. 로그 저장소와 **겹쳐서** 쓸 수도 있습니다.
6. **파일 저장소** — `FileMemberStorage` 를 만들면 프로그램을 꺼도 회원이 유지됩니다. 파일 입출력은 아직 안 배웠지만, **어디에 끼워 넣으면 되는지는 이미 정해져 있습니다.**
   👉 구조를 먼저 잡아 두면 나중에 배운 것을 **꽂아 넣기만 하면 된다**는 것이 이 설계의 가장 큰 이득입니다.
7. **회원도 등급을 나누기** — 추상 클래스 버전의 `Member` 3형제를 이 프로젝트에 가져와 보세요. 추상 클래스와 인터페이스를 **함께** 쓰게 됩니다. (`Array<Member?>` 로 바뀌는 것에 주의)
