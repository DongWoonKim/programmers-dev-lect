# 회원 관리 프로그램 만들기 (컬렉션 · data class)

> 배열로 만든 회원 관리 프로그램을 **컬렉션으로 다시 만듭니다.** 정원만큼 빈 칸을 미리 만들 필요도, 삭제할 때 뒤를 당길 필요도, 회원 수를 직접 셀 필요도 없어집니다. `MutableList` 와 `data class`, 그리고 컬렉션 함수로 같은 프로그램을 훨씬 짧게 만듭니다. **아래 Step을 순서대로 따라가면, 마지막 Step에서 프로그램이 완성됩니다.**

> **선행 과제**: `회원관리만들기(배열)` — 배열 버전의 "당기기" 코드를 직접 써 본 상태를 전제로 합니다.
> **선행 학습**: 컬렉션(List / Set / Map), data class, 컬렉션 함수(`filter` · `find` · `groupBy` 등)

---

배열 버전과 같은 프로그램입니다. 다만 **메뉴가 두 개 늘었습니다.**

|개념|어디서 쓰나|

|`ifBlank { }`|"Enter 만 누르면 기존 값 유지"|

## 4. 핵심 개념

### (1) 배열이 강요했던 세 가지 — 이 과제에서 사라지는 것

배열 버전에서 귀찮았던 코드는 대부분 **배열의 성질 때문에** 어쩔 수 없이 썼던 것입니다.

|배열이라서 해야 했던 일|왜 해야 했나|컬렉션에서는|
|---|---|---|
|정원만큼 빈 칸을 `""` 나 `Member()` 로 채우기|배열은 크기가 고정이라 만들 때 다 채워야 한다|**필요 없다.** 등록된 회원만 들어 있다|
|삭제할 때 뒤를 한 칸씩 **당기기** + 꼬리 정리|중간을 비울 수 없다|**필요 없다.** `removeAll` 한 줄|
|`memberCnt` 를 `var` 로 두고 `++` / `--`|배열은 "몇 칸이 채워졌는지" 모른다|**필요 없다.** `members.size` 가 답이다|

> ⭐ 코드가 짧아지는 것보다 중요한 것은 **틀릴 수 있는 자리가 사라진다**는 점입니다.
> `memberCnt++` 를 빠뜨리는 실수, 당기다가 인덱스를 하나 틀리는 실수는 **그 코드를 아예 안 쓰게 되면서** 생길 수 없게 됩니다.

### (2) `MutableList` — 크기가 변하는 저장소

```kotlin
// 배열 버전
private val members = Array(totalCnt) { Member() }   // 정원만큼 빈 회원을 미리 만든다

// 컬렉션 버전
private val members = mutableListOf<Member>()        // 비어 있는 채로 시작한다
```

```kotlin
members.add(member)      // 뒤에 붙인다. 자리 계산이 필요 없다
members.removeAll { }    // 지우면 뒤가 알아서 당겨진다
members.size             // 지금 몇 명인지 리스트가 안다
```

> ⚠️ **`val` 인데 어떻게 추가가 되나요?**
> `val` 은 **"이 이름표가 다른 객체를 가리키지 못한다"** 는 뜻이지, 객체의 내용을 얼리는 것이 아닙니다.
> `members = mutableListOf()` 는 막히지만 `members.add(...)` 는 됩니다. 배열에서 `val members` 인데 `members[0] = "홍길동"` 이 됐던 것과 같은 이야기입니다.

### (3) `data class` — 왜 `Member` 를 바꾸나

배열·추상클래스 버전의 `Member` 는 보통 클래스였습니다. 그래서 **내용이 같은 회원 둘이 서로 다른 것으로 취급**됐습니다.

```kotlin
class Member(val name: String, val email: String, val phone: String)

val a = Member("김철수", "kim@a.com", "010-1111-1111")
val b = Member("김철수", "kim@a.com", "010-1111-1111")

println(a == b)                 // false !!   내용이 같은데도
println(listOf(a).contains(b))  // false !!
println(setOf(a, b).size)       // 2     !!   중복 제거가 안 된다
```

`class` 앞에 `data` 한 단어를 붙이면 전부 해결됩니다.

```kotlin
data class Member(val name: String, val email: String, val phone: String)

println(a == b)                 // true
println(listOf(a).contains(b))  // true
println(setOf(a, b).size)       // 1
```

`data` 를 붙이면 주 생성자의 프로퍼티를 기준으로 다섯 가지가 자동으로 생깁니다.

|생성되는 것|무엇이 달라지나|
|---|---|
|`equals()`|`==` 가 **내용**을 비교한다|
|`hashCode()`|`Set` 의 중복 제거, `Map` 의 키가 제대로 동작한다|
|`toString()`|`Member(name=김철수, ...)` 로 찍힌다. 디버깅이 편해진다|
|`copy()`|**일부만 바꾼 새 객체**를 만든다 ⭐|
|`component1()`, `component2()` …|구조 분해 `val (name, email, phone) = member`|

> 💡 자바에서 IDE로 `equals` / `hashCode` 를 생성해 붙이던 수십 줄이 `data` 한 단어로 사라집니다.
> 자바 16의 `record` 와 비슷하지만, `copy()` 가 있다는 점이 다릅니다.

### (4) ⭐ `val` + `copy()` — 고치는 대신 갈아 끼운다

이 과제에서 **가장 중요한 개념**입니다.

배열·추상클래스 버전의 `Member` 는 프로퍼티가 전부 `var` 였습니다. 그래서 이런 코드가 가능했습니다.

```kotlin
// 추상클래스 버전의 updateMember
val member = manager.findByEmail(email)     // 저장소 안의 '그 객체'를 받아서
member.name = readln()                      // 직접 고친다
member.email = readln()
```

편했습니다. 인덱스를 들고 다닐 필요도 없었죠. **그런데 구멍이 있습니다.**

> `manager` 를 거치지 않고 고쳤으므로 **이메일 중복 검사를 건너뜁니다.** 다른 회원이 이미 쓰는 이메일로 바꿔도 막히지 않습니다.

이제 `Member` 의 프로퍼티를 전부 `val` 로 바꿉니다. 그러면 위 코드는 **컴파일조차 되지 않습니다.**

```kotlin
member.name = readln()      // ❌ Val cannot be reassigned
```

대신 새 값을 모아 `manager` 에게 넘기게 됩니다.

```kotlin
members[idx] = members[idx].copy(name = name, email = newEmail, phone = phone)
```

`copy()` 는 **준 인자만 바꾼 새 객체**를 만듭니다. 원본은 그대로 두고 리스트의 그 자리를 새 객체로 갈아 끼우는 것입니다.

> ⭐ **"고칠 수 없게 만들었더니 규칙이 지켜지더라"** — 이것이 `val` 을 쓰는 진짜 이유입니다.
> 수정이 반드시 `manager.update()` 를 지나가게 되므로, 검사를 빠뜨릴 방법이 없어집니다.
> `private set` 이 "밖에서 못 바꾸게" 막았다면, `val` 은 **"아무도 못 바꾸게"** 막습니다.

> 💡 `Set` 이나 `Map` 의 키로 쓸 값도 반드시 `val` 이어야 합니다. 넣은 뒤에 값을 바꾸면 `hashCode` 가 달라져서 **다시는 찾지 못하는 미아**가 됩니다.

### (5) 컬렉션 함수 — 반복문이 사라진다

같은 일을 하는 코드를 나란히 놓고 보세요.

|하는 일|배열 버전|컬렉션 버전|
|---|---|---|
|이메일로 찾기|`for (i in 0 until memberCnt) { if (...) return i }` + `return -1`|`members.find { it.email == email }`|
|중복 있나|위 함수 호출 후 `!= -1` 검사|`members.any { it.email == email }`|
|조건에 맞는 전부|세고 → 배열 만들고 → 다시 채우기 (3단계)|`members.filter { ... }`|
|위치 찾기|`findIndex(members, 1, email)`|`members.indexOfFirst { it.email == email }`|
|삭제|당기기 반복문 + `memberCnt--` + 꼬리 정리|`members.removeAll { it.email == email }`|
|잘라서 돌려주기|`members.copyOfRange(0, memberCnt)`|`members.toList()`|

> 💡 배열 버전의 `findIndex(members, col, value)` 에서 **매개변수가 전부 사라진 것**을 확인하세요.
> `members` 는 자기 프로퍼티라 넘길 필요가 없고, `col` 은 `it.email` 이라고 쓰면 되기 때문입니다.
> "열 번호 1이 이메일"이라는 것을 기억할 필요가 없어졌습니다.

**이름 규칙 세 가지**를 알아 두면 함수 이름을 외우지 않아도 됩니다.

|규칙|뜻|예|
|---|---|---|
|`OrNull`|못 찾으면 예외 대신 `null`|`first()` / `firstOrNull()`|
|`By` 와 `Of`|`By` 는 **원소**를, `Of` 는 **계산한 값**을 돌려준다|`maxByOrNull { it.age }` → `Member`, `maxOfOrNull { it.age }` → `Int`|
|`ed` 접미사|`ed` 가 붙으면 **새것**을 만들고, 없으면 **원본**을 고친다|`sorted()` / `sort()`|

### (6) `getAll()` 과 `toList()` — 읽기 전용과 복사는 다른 이야기

저장소를 밖으로 내보낼 때 주의할 점입니다.

```kotlin
fun getAll(): List<Member> = members          // ⚠️ 위험
fun getAll(): List<Member> = members.toList() // ✅ 안전
```

둘 다 반환형이 `List<Member>` 라서 받는 쪽은 `add` 를 못 씁니다. **그런데 위쪽은 저장소와 같은 객체입니다.**

```kotlin
val snapshot = manager.getAll()   // 3명을 받아 왔다
manager.add(...)                  // 저장소에 한 명 추가
println(snapshot.size)            // toList() 없으면 4 !!  내 목록이 멋대로 늘었다
```

|하는 일|무엇을 막나|
|---|---|
|반환형 `List<Member>`|받는 쪽이 `add` / `remove` 를 **못 하게** 한다|
|`toList()`|원본과의 **연결을 끊는다** (복사본을 만든다)|

> ⚠️ **둘은 서로 다른 문제를 해결합니다.** `List` 로 선언한다고 복사가 되는 것이 아닙니다.
> 배열 버전에서 `copyOfRange` 를 썼던 것과 같은 이유입니다.

> 💡 `toList()` 는 **얕은 복사**입니다. 리스트는 새로 생기지만 안에 든 `Member` 객체는 원본과 같은 것을 가리킵니다.
> 이 과제에서는 `Member` 가 `val` 뿐인 data class라 안에 든 값이 바뀔 일이 없어 문제가 되지 않습니다. **불변으로 만들면 복사 걱정이 줄어든다**는 것이 여기서도 이득입니다.

## 5. 파일 구조

```
src/main/kotlin/member/
├── Member.kt          회원 한 명 (data class)
├── MemberManager.kt   회원 목록과 규칙 (MutableList + 컬렉션 함수)
├── MemberApp.kt       메뉴와 입력, 출력
└── Main.kt            조립해서 실행
```

|파일|역할|배열 버전 대비|
|---|---|---|
|`Member`|이름·이메일·연락처|`class` → **`data class`**, `var` → **`val`**|
|`MemberManager`|저장·검색·규칙|`Array` → **`MutableList`**, 반복문 → **컬렉션 함수**|
|`MemberApp`|화면과 입력|**거의 그대로**|
|`Main`|요금제 선택 후 조립|샘플 데이터 투입이 추가됨|

> ⭐ **`MemberApp` 이 거의 그대로인 것에 주목하세요.**
> 저장 방식이 배열에서 리스트로 완전히 바뀌었는데도 화면 코드는 손댈 것이 거의 없습니다.
> 클래스를 역할별로 나눠 둔 덕분입니다. 배열 버전처럼 한 파일에 다 있었다면 전부 뒤집어야 했을 것입니다.

### Step 1. 회원 클래스 (`Member.kt`)

**목표**: 회원 한 명을 `data class` 로 만든다. 배열·추상클래스 버전에서 무엇이 사라지는지 확인한다.

**할 일**

1. `data class Member` 를 만들고 프로퍼티 3개를 **전부 `val`** 로 선언한다.
2. 화면에 보여 줄 문장은 `display` 라는 **커스텀 getter** 로 따로 만든다.

**힌트**

```kotlin
package member

data class Member(val name: String, val email: String, val phone: String) {

    // data class 가 만들어 주는 toString 은 Member(name=김철수, ...) 형태다.
    // 개발자가 보기에는 좋지만 사용자에게 보여 줄 문장은 아니므로 따로 만든다.
    val display: String
        get() = "[이름] $name, [이메일] $email, [연락처] $phone"
}
```

**이전 버전에서 사라진 것 두 가지**

```kotlin
// 사라짐 1) 빈 칸을 채우려고 만들었던 부 생성자
constructor() : this("", "", "")

// 사라짐 2) 손으로 만들었던 toString
override fun toString(): String = "[이름] $name, ..."
```

> **부 생성자가 왜 사라졌나?** 배열 버전은 `Array(totalCnt) { Member() }` 로 정원만큼 빈 회원을 미리 만들어야 했습니다. `MutableList` 는 필요할 때 늘어나므로 **"빈 회원"이라는 개념 자체가 없어집니다.**
> **`toString` 을 왜 `override` 하지 않았나?** `override` 하면 자동 생성된 `Member(name=..., email=...)` 이 사라집니다. 디버깅용 출력은 남겨 두는 편이 낫기 때문에 화면용은 `display` 로 따로 뒀습니다. 물론 `override` 해도 됩니다. **무엇을 잃는지 알고 고르는 것이 중요합니다.**
> `display` 는 저장 공간을 쓰지 않고 **읽을 때마다 계산**하는 커스텀 getter 입니다.

**확인**

```kotlin
fun main() {
    val a = Member("김철수", "kim@a.com", "010-1111-1111")
    val b = Member("김철수", "kim@a.com", "010-1111-1111")

    println(a == b)             // true      <- data 를 빼면 false
    println(setOf(a, b).size)   // 1         <- data 를 빼면 2
    println(a)                  // Member(name=김철수, ...)
    println(a.display)          // [이름] 김철수, [이메일] ...
    println(a.copy(name = "김영수"))   // 이름만 바뀐 새 객체
}
```

`data` 를 뗐다 붙였다 하면서 결과가 어떻게 달라지는지 **직접 확인해 보세요.** 이 과제의 출발점입니다.

### Step 2. 저장소 뼈대 (`MemberManager.kt`)

**목표**: `MutableList` 저장소와 정원·인원수 프로퍼티를 만든다.

**할 일**

1. 생성자로 `planNo` 를 받아 `totalCnt` 를 계산한다.
2. 저장소를 `mutableListOf<Member>()` 로 만들고 `private` 으로 감춘다.
3. `memberCnt` 와 `isFull` 을 **커스텀 getter** 로 만든다.

**힌트**

```kotlin
package member

class MemberManager(planNo: Int) {

    val totalCnt = planNo * 10

    // 빈 칸을 미리 만들지 않는다. 지금 등록된 회원만 들어 있다.
    private val members = mutableListOf<Member>()

    val memberCnt: Int
        get() = members.size

    val isFull: Boolean
        get() = members.size >= totalCnt
}
```

**이전 버전에서 사라진 것**

```kotlin
// 사라짐) 인원수를 직접 세던 프로퍼티
var memberCnt = 0
    private set
```

> ⭐ **이것이 이 Step의 핵심입니다.** 배열 버전은 "몇 칸이 채워졌는지" 배열이 모르므로 사람이 세야 했습니다. `add` 에서 `++`, `delete` 에서 `--` 를 **직접** 해야 했고, 하나라도 빠뜨리면 조용히 틀립니다.
> 리스트는 자기 크기를 알고 있습니다. **세는 코드가 없으면 세다가 틀릴 일도 없습니다.**
> `private set` 으로 "밖에서 못 바꾸게" 막던 문제가, 아예 **저장하지 않음**으로써 사라졌습니다.

> 💡 `planNo` 앞에 `val` 을 붙이지 않은 것은 배열·추상클래스 버전과 같습니다. `totalCnt` 를 계산하는 데만 쓰고 버릴 값이라 프로퍼티로 남길 필요가 없습니다.

**확인**: `MemberManager(2).totalCnt` 가 `20`, `memberCnt` 가 `0`, `isFull` 이 `false` 면 성공.

### Step 3. 조회 — `find` 와 `toList`

**목표**: 반복문 없이 회원을 찾는다. 저장소를 안전하게 밖으로 내보낸다.

**할 일**

1. `findByEmail(email): Member?` — `find` 로 한 명 찾기. 없으면 `null`.
2. `findByName(name): Member?` — 같은 방식, 조건만 다르게.
3. `searchByName(keyword): List<Member>` — `filter` 로 **여러 명** 찾기. (메뉴 7에서 쓴다)
4. `getAll(): List<Member>` — `toList()` 로 복사본을 돌려준다.

**힌트**

```kotlin
// find 는 firstOrNull 의 다른 이름이다. 못 찾으면 예외 대신 null 이다.
fun findByEmail(email: String): Member? = members.find { it.email == email }

fun findByName(name: String): Member? = members.find { it.name == name }

// 이름에 keyword 가 들어간 회원을 전부 찾는다.
fun searchByName(keyword: String): List<Member> =
    members.filter { it.name.contains(keyword) }

// toList() 를 빼면 저장소와 같은 객체가 밖으로 나간다. (핵심 개념 6)
fun getAll(): List<Member> = members.toList()
```

> ⭐ **배열 버전의 `findIndex` 가 통째로 사라졌습니다.** 인덱스를 찾아서 `members[idx]` 를 꺼내던 두 단계가 한 줄이 됐고, "인덱스는 밖으로 나가면 안 된다"며 `private` 을 붙일 일도 없어졌습니다.
> `{ it.email == email }` 에서 `it` 은 리스트의 원소 하나, 즉 `Member` 입니다. 이름을 직접 붙이려면 `{ m -> m.email == email }` 로 씁니다.
> **`-1` 이 `null` 로 바뀐 것**은 추상클래스 버전과 같습니다. 받는 쪽이 null 검사를 **강제로** 하게 되는 것이 장점입니다.

> ⚠️ **`find` 와 `filter` 를 구분하세요.** `find` 는 한 명(`Member?`), `filter` 는 여러 명(`List<Member>`) 입니다. 이메일은 고유값이라 `find`, 이름은 겹칠 수 있으니 `filter` 가 어울립니다.

**확인**: 없는 이메일로 `findByEmail` 을 부르면 `null` 이 나오고, `getAll()` 을 받아 둔 뒤 회원을 추가해도 **받아 둔 목록의 크기가 그대로면** 성공.

### Step 4. 회원 추가 — `any` 로 중복 검사

**목표**: 정원과 이메일 중복을 검사하고 리스트에 추가한다.

**할 일**

1. `isFull` 이면 `false` 를 돌려준다.
2. 같은 이메일이 이미 있으면 `false` 를 돌려준다.
3. `members.add(member)` 후 `true`.

**힌트**

```kotlin
fun add(member: Member): Boolean {
    if (isFull) return false                                    // 정원 초과
    if (members.any { it.email == member.email }) return false   // 이메일 중복

    members.add(member)     // 자리 계산도, memberCnt++ 도 필요 없다

    return true
}
```

> **`any` 는 "조건에 맞는 것이 하나라도 있는가"** 를 묻습니다. `find { ... } != null` 과 같은 뜻이지만, 객체가 필요 없고 있는지만 궁금할 때는 `any` 가 의도를 더 잘 드러냅니다.
> 배열 버전의 `members[memberCnt] = member; memberCnt++` 가 `members.add(member)` 한 줄이 됐습니다. **"빈 칸의 위치를 계산해서 넣는다"가 "그냥 뒤에 붙인다"로** 바뀌었습니다.
> `println` 을 하지 않는 것은 추상클래스 버전과 같습니다. **화면에 무엇을 띄울지는 `MemberApp` 이 정할 일**입니다.

**확인**: 같은 이메일로 두 번 추가하면 두 번째가 `false`, 정원만큼 채운 뒤 추가하면 `false` 면 성공.

### Step 5. ⭐ 회원 삭제 — 당기기가 사라진다

**목표**: 배열 버전에서 가장 길었던 함수를 **한 줄로** 만든다.

**할 일**: `removeAll` 로 조건에 맞는 회원을 지운다. 끝입니다.

**힌트**

```kotlin
fun delete(email: String): Boolean = members.removeAll { it.email == email }
```

**배열 버전과 나란히 보기**

```kotlin
// [배열 버전]
fun delete(email: String): Boolean {
    val idx = findIndex(email)
    if (idx == -1) return false

    for (i in idx until memberCnt - 1) {    // 당기기
        members[i] = members[i + 1]
    }
    memberCnt--                             // 인원수 줄이기
    members[memberCnt] = Member()           // 꼬리 정리

    return true
}

// [컬렉션 버전]
fun delete(email: String): Boolean = members.removeAll { it.email == email }
```

> ⭐ **이 Step이 이 과제의 하이라이트입니다.** 배열 버전에서 "당기기 → `memberCnt--` → 꼬리 정리" 순서를 지켜야 했던 것, 순서를 바꾸면 마지막 회원이 사라지던 것, `until` 범위를 하나 틀리기 쉬웠던 것이 **전부 없어집니다.**
> 리스트는 지우면 **뒤가 알아서 당겨지고 크기도 알아서 줄어듭니다.**
> `removeAll` 은 하나라도 지웠으면 `true` 를 돌려주므로 그대로 함수의 결과가 됩니다.

> 💡 **순회 도중 삭제 문제도 함께 해결됩니다.** `for (m in members) { if (...) members.remove(m) }` 는 `ConcurrentModificationException` 으로 죽습니다. `removeAll { }` 은 그 문제를 대신 막아 줍니다. **조건으로 지우고 싶을 때는 직접 돌지 말고 `removeAll` 을 쓰세요.**

**확인**: 가운데 회원을 지워도 목록이 빈칸 없이 이어지고 인원수가 줄면 성공. **당기기 코드를 한 줄도 쓰지 않았는지** 확인하세요.

### Step 6. ⭐ 회원 수정 — `copy` 로 갈아 끼우기

**목표**: `val` 이 된 `Member` 를 수정한다. 그 과정에서 배열 버전에 있던 **설계 구멍을 막는다.**

**할 일**

1. `indexOfFirst` 로 수정할 회원의 위치를 찾는다. 없으면 `false`.
2. 이메일을 **바꾸는 경우에만** 다른 회원과 겹치는지 검사한다.
3. `copy()` 로 새 객체를 만들어 그 자리에 갈아 끼운다.

**힌트**

```kotlin
fun update(email: String, name: String, newEmail: String, phone: String): Boolean {
    // indexOfFirst 는 조건에 맞는 첫 번째 위치를 준다. 없으면 -1 이다.
    val idx = members.indexOfFirst { it.email == email }
    if (idx == -1) return false

    // 이메일을 바꾸는 경우에만 중복을 검사한다. 자기 자신은 걸리면 안 되기 때문이다.
    if (newEmail != email && members.any { it.email == newEmail }) return false

    // 고치는 대신 새로 만들어 갈아 끼운다.
    members[idx] = members[idx].copy(name = name, email = newEmail, phone = phone)

    return true
}
```

> ⭐ **`if (newEmail != email && ...)` 이 이 Step에서 가장 생각이 필요한 줄입니다.**
> 앞 조건을 빼면 어떻게 될까요? 이메일을 그대로 두고 이름만 바꾸려 할 때, **자기 자신이 중복으로 걸려서** 수정이 거부됩니다. 직접 빼 보고 확인해 보세요.

> ⭐ **왜 이 함수가 생겼나?** 배열·추상클래스 버전에서는 `MemberApp` 이 `findByEmail` 로 받은 객체의 `var` 를 직접 고쳤습니다. `manager` 를 거치지 않으니 **이메일 중복 검사를 건너뛰는 구멍**이 있었죠.
> `Member` 를 `val` 뿐인 data class로 만들자 그 방법이 **컴파일되지 않게** 되었고, 수정이 반드시 이 함수를 지나가게 되었습니다. **불변으로 만든 것이 규칙을 강제한 셈입니다.**

> 💡 `copy()` 는 **준 인자만** 바꿉니다. `member.copy(name = "김영수")` 처럼 하나만 바꿀 수도 있습니다.
> 반환값이 `Boolean` 하나라 "없음"과 "중복"을 구분하지 못합니다. `MemberApp` 에서 회원 존재를 **먼저 확인**한 뒤 부르면, `false` 는 중복뿐이라 구분이 됩니다. (Step 7에서 그렇게 씁니다)

**확인**: 이름만 바꾸기가 되고, 다른 회원이 쓰는 이메일로 바꾸면 거부되고, 없는 회원을 수정하면 `false` 면 성공.

### Step 7. 화면 담당 (`MemberApp.kt`) + `Main.kt`

**목표**: 메뉴를 만들고 `MemberManager` 와 연결한다. **배열 버전에서 거의 안 바뀐다는 것**을 확인한다.

**할 일**

1. 생성자로 `MemberManager` 를 받는다.
2. `printMenu` / `start` 로 메뉴를 반복한다. (메뉴 7·8은 Step 8에서)
3. 추가·조회·전체조회·삭제를 연결한다.
4. `updateMember` 만 **새로 쓴다.**

**힌트 (거의 그대로인 부분)**

```kotlin
private fun updateMember() {
    println("수정할 회원의 이메일을 입력하세요.")
    val email = readln()

    val member = manager.findByEmail(email)
    if (member == null) {
        println("찾으시는 회원이 없습니다.")
        return
    }

    println("현재 정보 → ${member.display}")

    // 배열 버전: member.name = readln()   <- val 이 되면서 컴파일 에러
    // ifBlank 는 빈 문자열일 때 대신 쓸 값을 정한다. Enter 만 치면 기존 값이 유지된다.
    println("새 이름을 입력하세요. (Enter 만 누르면 유지)")
    val name = readln().ifBlank { member.name }
    println("새 이메일을 입력하세요. (Enter 만 누르면 유지)")
    val newEmail = readln().ifBlank { member.email }
    println("새 연락처를 입력하세요. (Enter 만 누르면 유지)")
    val phone = readln().ifBlank { member.phone }

    // 위에서 회원이 있다는 것은 확인했다. 그러므로 false 는 이메일 중복뿐이다.
    if (manager.update(email, name, newEmail, phone)) {
        println("수정이 완료되었습니다.")
    } else {
        println("이미 사용 중인 이메일입니다.")
    }
}
```

> ⭐ **`MemberApp` 이 얼마나 안 바뀌었는지 세어 보세요.** 저장 방식이 배열에서 리스트로 완전히 바뀌었는데 고친 곳은 `updateMember` 하나뿐입니다.
> `MemberApp` 은 저장소가 리스트인지 배열인지 **모릅니다.** 이것이 클래스를 역할별로 나눠 둔 이득입니다.
> 샘플 데이터를 `listOf(...).forEach { manager.add(it) }` 로 넣은 것에도 주목하세요. **네 줄의 `add` 호출 대신 목록 하나와 `forEach` 한 번**입니다.

**확인**: 배열 버전과 똑같이 동작하면 성공. 여기까지가 "같은 프로그램 다시 만들기"입니다.

### Step 8. 컬렉션이라서 생긴 새 기능 (완성!)

**목표**: 배열로는 만들기 번거로웠던 기능을 추가한다.

**할 일**

1. `MemberManager` 에 `sortedByName` / `groupByDomain` / `duplicatedNames` 를 만든다.
2. `MemberApp` 에 메뉴 7(이름검색)과 8(통계)을 연결한다.

**힌트 (`MemberManager`)**

```kotlin
// 이름순으로 정렬한 새 리스트. 원본의 등록 순서는 그대로 둔다.
fun sortedByName(): List<Member> = members.sortedBy { it.name }

// 이메일 도메인으로 묶는다.  {naver.com=[...], gmail.com=[...]}
// substringAfter 는 "@" 뒤를 잘라 준다. "@" 가 없으면 두 번째 인자를 대신 쓴다.
fun groupByDomain(): Map<String, List<Member>> =
    members.groupBy { it.email.substringAfter("@", "(도메인없음)") }

// 같은 이름을 쓰는 회원. groupBy 로 묶은 뒤 2명 이상인 것만 남긴다.
fun duplicatedNames(): Map<String, List<Member>> =
    members.groupBy { it.name }.filter { it.value.size > 1 }
```

**힌트 (`MemberApp`)**

```kotlin
private fun searchByName() {
    println("검색할 이름의 일부를 입력하세요.")
    val keyword = readln()

    val found = manager.searchByName(keyword)
    if (found.isEmpty()) {
        println("검색 결과가 없습니다.")
        return
    }

    println("${found.size}명을 찾았습니다.")
    found.forEachIndexed { i, member -> println("${i + 1}. ${member.display}") }
}

private fun printStatistics() {
    if (manager.memberCnt == 0) {
        println("등록된 회원이 없습니다.")
        return
    }

    // Map 을 돌면서 키와 값을 바로 쪼갠다. (구조 분해)
    println("[이메일 도메인별]")
    manager.groupByDomain().forEach { (domain, list) ->
        // joinToString 은 리스트를 문자열 하나로 이어 붙인다. 마지막 쉼표를 걱정할 필요가 없다.
        println("  $domain : ${list.size}명  (${list.joinToString(", ") { it.name }})")
    }

    println("[이름순]")
    println("  ${manager.sortedByName().joinToString(", ") { it.name }}")

    val dup = manager.duplicatedNames()
    if (dup.isNotEmpty()) {
        println("[이름이 겹치는 회원]")
        dup.forEach { (name, list) ->
            println("  $name : ${list.size}명  (${list.joinToString(", ") { it.email }})")
        }
    }
}
```

> **`groupBy` 가 돌려주는 것은 `Map<String, List<Member>>`** 입니다. 키는 묶은 기준(도메인), 값은 그 기준에 해당하는 회원들의 목록입니다.
> `forEach { (domain, list) -> ... }` 의 괄호가 **구조 분해**입니다. `Map.Entry` 를 키와 값 두 개로 쪼개 줍니다. `for ((k, v) in map)` 과 같은 문법입니다.
> `joinToString(", ") { it.name }` 은 "각 회원에서 이름만 뽑아 쉼표로 이어 붙이라"는 뜻입니다. **반복문 + `if (마지막이 아니면 쉼표)` 가 통째로 사라집니다.**
> `sortedBy` 에 `ed` 가 붙은 것에 주목하세요. **새 리스트를 만들고 원본 순서는 건드리지 않습니다.**

> 💡 **이 기능들을 배열로 만들어 보면** 왜 컬렉션을 쓰는지 확실히 알게 됩니다. 도메인별 통계 하나만 해도 도메인 목록을 따로 모으고, 중복을 제거하고, 다시 세는 코드가 필요합니다. 도전 과제 1번으로 남겨 두겠습니다.

## 7. 네 버전 비교

|                |배열 버전|추상 클래스 버전|인터페이스 버전|**컬렉션 버전**|
|---|---|---|---|---|
|무엇을 배우나|배열의 한계|다형성|규약과 교체|**자료구조와 불변**|
|핵심 문법|최상위 함수 · 배열|`abstract class`|`interface` · `by`|**`MutableList` · `data class`**|
|회원 표현|`Array<String>` 3칸|`Member` 3형제|`Member` 하나|**`data class Member` (전부 `val`)**|
|저장소|`Array(정원)`|`Array<Member?>`|`Array<Member?>`|**`mutableListOf<Member>()`**|
|빈 칸 처리|`""` 로 채우기|`null` 처리 (`?.`, `!!`)|`null` 처리|**빈 칸이 없다**|
|인원수|최상위 `var` + `++`|`var` + `private set`|`override var`|**`get() = members.size`**|
|검색|`findIndex(members, col, v)`|`findIndex(email)` (private)|`findIndex` (private)|**`find { it.email == email }`**|
|삭제|당기기 + 꼬리 정리|당기기 + 꼬리 정리|당기기 + 꼬리 정리|**`removeAll { }` 한 줄**|
|수정|`members[idx][0] = ...`|`member.name = ...`|`member.name = ...`|**`copy()` 로 갈아 끼우기**|
|수정 시 중복 검사|없음 (구멍)|없음 (구멍)|없음 (구멍)|**막았다** ⭐|

> **컬렉션 버전이 제일 좋은가?** 그런 이야기가 아닙니다. **바뀌는 것은 "무엇을 신경 쓰는가"** 입니다.
> 배열 버전은 **메모리를 내가 관리**합니다. 몇 칸을 쓸지, 빈 칸을 무엇으로 채울지, 지운 자리를 어떻게 메울지 전부 내가 정합니다.
> 컬렉션 버전은 그 일을 라이브러리에 맡기고, 대신 **"이 값이 바뀌어도 되는가"** 를 신경 씁니다. `val` 이냐 `var` 냐, 복사본이냐 원본이냐 하는 고민이 그것입니다.
> 관리할 것이 사라진 게 아니라 **관리할 층이 한 단계 올라간 것**입니다.

> 💡 **네 버전은 서로 배타적이지 않습니다.** 인터페이스 버전의 `MemberStorage` 를 그대로 두고 구현만 `ListMemberStorage` 로 바꾸면 두 과제가 합쳐집니다. 도전 과제 4번입니다.

## 8. 최종 완성 체크리스트

- [ ] `data class Member` — 프로퍼티가 **전부 `val`**
- [ ] `display` 커스텀 getter (자동 생성 `toString` 을 지우지 않았다)
- [ ] 부 생성자 `Member()` 를 만들지 **않았다**
- [ ] `private val members = mutableListOf<Member>()`
- [ ] `memberCnt` 를 저장하지 않고 `get() = members.size` 로 계산
- [ ] `find` / `filter` / `any` / `indexOfFirst` / `removeAll` 을 각각 한 번 이상 썼다
- [ ] `getAll()` 이 `toList()` 로 복사본을 돌려준다 ⭐
- [ ] `update` 가 `copy()` 로 갈아 끼우고, **이메일 중복도 검사**한다 ⭐
- [ ] `update` 의 중복 검사에 `newEmail != email` 조건이 있다 ⭐
- [ ] 당기기 반복문 · `memberCnt++` · 꼬리 정리가 **한 줄도 없다** ⭐
- [ ] `MemberApp` 에서 `updateMember` 말고는 배열 버전과 거의 같다
- [ ] 메뉴 7(`filter`) · 8(`groupBy` · `sortedBy` · `joinToString`) 동작

## 9. 개선 & 도전 과제

**먼저 다듬으면 좋은 점**

1. **빈 입력 막기** — 이름이나 이메일에 그냥 Enter를 치면 `""` 가 저장됩니다.
   ```kotlin
   if (name.isBlank()) { println("이름은 비워 둘 수 없습니다."); return }
   ```

2. **이메일 형식 검사** — `require` 나 `init` 블록으로 `Member` 자신이 검사하게 할 수 있습니다.
   ```kotlin
   data class Member(val name: String, val email: String, val phone: String) {
       init { require(email.contains("@")) { "이메일 형식이 아닙니다" } }
   }
   ```
   > 다만 예외가 나면 프로그램이 죽습니다. **어디서 검사할지**(입력 직후 / 생성자 / manager)를 정하는 것도 설계입니다.

3. **`update` 의 반환값을 넓히기** — 지금은 `Boolean` 이라 "없음"과 "중복"을 구분하지 못합니다.
   ```kotlin
   enum class UpdateResult { OK, NOT_FOUND, DUPLICATE_EMAIL }
   ```
   `MemberApp` 이 `when` 으로 분기하면 안내 문구가 정확해집니다.

**확장 도전 과제**

1. **배열로 통계 만들어 보기** ⭐ — 메뉴 8(도메인별 통계)을 **배열만으로** 만들어 보세요. 도메인 목록 모으기 → 중복 제거 → 다시 세기가 필요합니다. 다 만든 뒤 `groupBy` 한 줄과 비교해 보면, 컬렉션 함수가 무엇을 대신해 주는지 확실히 알게 됩니다.

2. **동명이인 조회** — 메뉴 3(이름 조회)이 지금은 `find` 라서 **처음 한 명만** 나옵니다. `filter` 로 바꿔 모두 나오게 해 보세요. 반환형이 `Member?` 에서 `List<Member>` 로 바뀌면 `MemberApp` 은 어떻게 달라져야 할까요?

3. **정렬 기준 늘리기** — 이름순 말고 등록순 · 도메인순으로도 볼 수 있게 해 보세요.
   ```kotlin
   members.sortedWith(compareBy({ it.email.substringAfter("@") }, { it.name }))
   ```
   `compareBy` 는 **여러 기준을 순서대로** 적용합니다. 앞 기준이 같을 때만 뒤 기준을 봅니다.

4. **인터페이스 버전과 합치기** ⭐ — 인터페이스 과제의 `MemberStorage` 규약을 가져와 `ListMemberStorage` 를 만들어 보세요. `Main.kt` 한 줄만 바꿔서 배열 저장소 ↔ 리스트 저장소를 **갈아 끼울 수 있는지** 확인하는 것이 핵심입니다. 두 과제가 자연스럽게 이어집니다.

5. **`Set` 으로 중복 막기** — 저장소를 `mutableSetOf<Member>()` 로 바꾸면 어떻게 될까요?
   - 완전히 똑같은 회원은 자동으로 걸러집니다.
   - **그런데 이메일만 같고 이름이 다른 회원은 못 막습니다.** `data class` 의 `equals` 는 **모든** 프로퍼티를 보기 때문입니다.
   - 이메일만으로 같음을 판단하게 하려면 `equals` / `hashCode` 를 직접 만들어야 합니다. 그때는 `data` 를 떼는 것이 정직합니다.
   👉 **"자동 생성된 `equals` 가 내가 원하는 기준인가"** 를 따져 보는 좋은 연습입니다.

6. **`Map` 으로 바꾸기** — `mutableMapOf<String, Member>()` (키 = 이메일)로 바꾸면 어떻게 될까요?
   - 이메일 검색이 **전체를 훑지 않고** 바로 찾아집니다. 회원이 10만 명이면 큰 차이입니다.
   - 중복 검사도 `containsKey` 한 번입니다.
   - **대신 등록 순서와 이름 검색이 불편해집니다.** 무엇을 얻고 무엇을 잃는지 직접 판단해 보세요.

7. **통계 더 만들기** — `count` · `sumOf` · `maxByOrNull` · `partition` 을 써서 만들어 보세요.
   ```kotlin
   members.count { it.email.endsWith("gmail.com") }
   members.partition { it.phone.startsWith("010") }    // (맞는 것, 아닌 것) 두 덩어리로
   ```

8. **파일 저장** — 프로그램을 꺼도 회원이 유지되도록 저장/불러오기를 만들어 보세요.
   `joinToString("\n")` 으로 내보내고, 읽을 때는 `split(",")` 후 `map { Member(...) }` 으로 되돌립니다. **컬렉션 함수가 파일 입출력에서도 그대로 쓰입니다.**

### 한 줄 정리

> 이 과제는 **배열 버전에서 "어쩔 수 없이 썼던 코드"를 지워 나가는** 연습입니다.
> 빈 칸 채우기, 당기기, 인원수 세기는 배열의 사정이었지 회원 관리의 본질이 아니었습니다. 그 코드가 사라진 자리에 `filter` 와 `groupBy` 같은 **진짜 하고 싶었던 일**이 들어옵니다.
> 그리고 `var` 를 `val` 로 바꾸는 것만으로 **배열 버전에 있던 설계 구멍 하나가 저절로 막힙니다.** 좋은 자료구조는 코드를 짧게 만드는 데서 그치지 않고, **틀린 코드를 아예 못 쓰게 만듭니다.**
