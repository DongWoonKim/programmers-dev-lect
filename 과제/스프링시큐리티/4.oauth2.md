# OAuth2로 카카오 소셜 로그인 만들기 (인가 코드 방식 + 우리 JWT 발급)

> 3번 과제에서 "우리 회원"의 토큰 로그인을 완성했다면, 이번엔 **입구를 하나 더** 열어요 — 카카오 계정으로 로그인하기.
> 핵심 그림은 이거예요: **카카오는 "이 사람이 카카오 회원 OO이 맞다"는 인증만 해주고, 그 결과를 우리 서비스의 JWT로 바꿔서 발급하는 건 3번 과제에서 만든 체계 그대로예요.** 소셜 로그인은 인증 체계를 갈아엎는 게 아니라 입구만 추가하는 거예요.
> 코드보다 중요한 건 흐름이에요: **비밀번호를 받지 않고도 어떻게 신뢰하는가(권한 위임), 프레임워크가 어디까지 해주고 우리는 어느 "틈"에 코드를 끼워 넣는가.**
>
> 💡 각 Step의 **힌트는 접혀 있어요.** 먼저 스스로 만들어 보고 막히면 펼치세요.

**`application.yaml`** — registration(우리 앱 등록 정보) + provider(카카오 엔드포인트)
```yaml
spring:
  security:
    oauth2:
      client:
        # [registration] "우리 서비스"가 카카오에 등록한 Client 정보.
        # 키 이름(kakao)이 registrationId가 되어 규약 URL에 그대로 쓰인다:
        #   로그인 진입: /oauth2/authorization/kakao  /  콜백: /login/oauth2/code/kakao
        registration:
          kakao:
            client-id: <카카오 콘솔의 REST API 키>
            client-secret: <카카오 콘솔 > 보안 > Client Secret>
            # 콘솔의 Redirect URI 등록값과 "완전히 일치"해야 한다 (불일치 시 KOE006)
            redirect-uri: "{baseUrl}/login/oauth2/code/kakao"
            authorization-grant-type: authorization_code
            # 카카오는 client_secret을 Basic 헤더가 아니라 POST 본문으로 받는다.
            # 빼면 토큰 교환에서 인증 실패 — 제공자별로 다른 대표적 지점
            client-authentication-method: client_secret_post
            client-name: Kakao
            scope:
              - profile_nickname
              # - account_email  # 비즈 앱 전환 후에만 사용 가능
        # [provider] 카카오는 Spring이 모르는 제공자라 엔드포인트를 직접 알려준다
        provider:
          kakao:
            authorization-uri: https://kauth.kakao.com/oauth/authorize   # 표준 흐름 1: 인가 페이지
            token-uri: https://kauth.kakao.com/oauth/token               # 표준 흐름 4~5: 코드→토큰 교환
            user-info-uri: https://kapi.kakao.com/v2/user/me             # 표준 흐름 6: 사용자 정보 조회
            # user-info 응답에서 "사용자 식별자"로 쓸 최상위 필드 이름 (필수!)
            user-name-attribute: id
```

**`config/oauth/AuthProvider.java`** — 가입 경로 enum
```java
// SNS 제공자뿐 아니라 LOCAL(자체 가입)도 값으로 가진다 —
// User.provider 컬럼이 @Enumerated(STRING)으로 이 enum과 매핑되므로,
// DB에 들어갈 수 있는 모든 값이 여기에 있어야 한다.
public enum AuthProvider {
    LOCAL,   // 자체 가입. OAuth2 흐름에서는 쓰이지 않는다
    KAKAO;   // 새 제공자(네이버 등)를 추가하면 여기에 상수가 늘어난다

    // registrationId("kakao") → enum. yaml registration의 키 이름과
    // enum 상수 이름이 일치해야 한다는 암묵적 규약이 이 한 줄에 숨어 있다
    public static AuthProvider from(String registrationId) {
        return AuthProvider.valueOf(registrationId.toUpperCase());
    }
}
```

**`config/oauth/KakaoUserInfo.java`** — 카카오 응답 파서
```java
// 카카오 user-info(/v2/user/me) 응답에서 필요한 값을 꺼내는 구현체.
// 응답은 2~3단계로 중첩: { "id": 123, "kakao_account": { "email": ..., "profile": { "nickname": ... } } }
// 주의: 카카오는 미동의 항목을 null이 아니라 "키 생략"으로 준다 → 모든 중첩 접근에 널 가드 필수.
// 여기서는 값 추출까지만 하고, "email 없으면 거부" 같은 정책은 상위 서비스의 일이다.
public record KakaoUserInfo(Map<String, Object> attributes) implements OAuth2UserInfo {

    @Override
    public String id() {
        Object id = attributes.get("id");   // JSON 숫자(Long)로 온다
        return id == null ? null : String.valueOf(id);
    }

    @Override
    public String email() {
        Map<String, Object> account = kakaoAccount();
        return account == null ? null : (String) account.get("email");
    }

    @Override
    public String name() {
        Map<String, Object> profile = profile();
        return profile == null ? null : (String) profile.get("nickname");
    }

    @Override
    public String imageUrl() {
        Map<String, Object> profile = profile();
        return profile == null ? null : (String) profile.get("profile_image_url");
    }

    @SuppressWarnings("unchecked")
    private Map<String, Object> kakaoAccount() {
        return (Map<String, Object>) attributes.get("kakao_account");
    }

    @SuppressWarnings("unchecked")
    private Map<String, Object> profile() {
        Map<String, Object> account = kakaoAccount();
        return account == null ? null : (Map<String, Object>) account.get("profile");
    }
}
```

**`config/oauth/OAuth2UserInfoFactory.java`**
```java
public final class OAuth2UserInfoFactory {

    private OAuth2UserInfoFactory() {}

    public static OAuth2UserInfo of(AuthProvider provider, Map<String, Object> attributes) {
        return switch (provider) {
            case KAKAO -> new KakaoUserInfo(attributes);
            // switch식은 모든 enum 상수를 다루도록 컴파일러가 강제한다 —
            // 새 제공자를 enum에 넣는 순간 "여기도 고치라"고 컴파일 에러로 알려준다
            case LOCAL -> throw new IllegalArgumentException("LOCAL은 OAuth2 제공자가 아닙니다.");
        };
    }
}
```

**`config/oauth/CustomOAuth2User.java`** — CustomUserDetails의 OAuth2 버전
```java
// 자체 로그인: UserDetails ← CustomUserDetails가 User를 감싼다
// 소셜 로그인: OAuth2User  ← 이 클래스가 User를 감싼다 (같은 자리의 어댑터)
@Getter
public class CustomOAuth2User implements OAuth2User {

    private final User user;                        // 우리 DB 회원. 미가입이면 null
    private final AuthProvider provider;
    private final OAuth2UserInfo userInfo;
    private final Map<String, Object> attributes;   // 제공자가 준 원시 속성 맵
    private final String nameAttributeKey;          // 식별자 키 (kakao=id)

    public CustomOAuth2User(User user, AuthProvider provider, OAuth2UserInfo userInfo,
                            Map<String, Object> attributes, String nameAttributeKey) {
        this.user = user;
        this.provider = provider;
        this.userInfo = userInfo;
        this.attributes = attributes;
        this.nameAttributeKey = nameAttributeKey;
    }

    // 미가입: SNS 인증만 통과, 가입 동의 전이므로 user가 없다.
    // 생성자 오버로딩 대신 "이름 있는" 정적 팩토리 — 호출부에서 의도가 읽힌다
    public static CustomOAuth2User unregistered(AuthProvider provider, OAuth2UserInfo userInfo,
                                                Map<String, Object> attributes, String nameAttributeKey) {
        return new CustomOAuth2User(null, provider, userInfo, attributes, nameAttributeKey);
    }

    // SuccessHandler가 "로그인 완료 vs 가입 안내" 분기에 사용
    public boolean isRegistered() {
        return user != null;
    }

    @Override
    public Map<String, Object> getAttributes() {
        return attributes;
    }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        if (user == null) {
            return List.of(new SimpleGrantedAuthority("ROLE_GUEST")); // 미가입 임시 권한
        }
        return List.of(new SimpleGrantedAuthority(user.getRole().name()));
    }

    @Override
    public String getName() {
        return String.valueOf(attributes.get(nameAttributeKey));
    }
}
```

**`service/CustomOAuth2UserService.java`** — 파이프라인의 첫 번째 훅
```java
// user-info 조회 "직후" 호출된다. "제공자의 회원"을 "우리 회원"으로 연결하는 단계.
// UserDetailService.loadUserByUsername()과 정확히 같은 자리의 부품이다.
@Service
@RequiredArgsConstructor
public class CustomOAuth2UserService extends DefaultOAuth2UserService {

    private final UserRepository userRepository;

    @Override
    @Transactional // 기존 회원 프로필 갱신(dirty checking)이 트랜잭션 안에서 일어나도록
    public OAuth2User loadUser(OAuth2UserRequest userRequest) throws OAuth2AuthenticationException {
        // (1) 표준 동작 위임: 부모가 user-info HTTP 호출까지 해준다. 딱 한 번만 부를 것!
        OAuth2User oAuth2User = super.loadUser(userRequest);

        // (2) 어떤 제공자로 로그인했는지 = yaml registration의 키
        String registrationId = userRequest.getClientRegistration().getRegistrationId();

        // (3) yaml provider의 user-name-attribute 값(kakao=id)이 여기로 흘러온다
        String nameAttributeKey = userRequest.getClientRegistration()
                .getProviderDetails().getUserInfoEndpoint().getUserNameAttributeName();

        // (4) 원시 맵 → 제공자별 파서. 이 아래로는 어느 제공자인지 아무도 모른다(다형성)
        AuthProvider provider = AuthProvider.from(registrationId);
        OAuth2UserInfo userInfo = OAuth2UserInfoFactory.of(provider, oAuth2User.getAttributes());

        // (5) 이메일은 우리 User의 필수 정보 — 못 받으면 로그인 거부.
        //     반드시 OAuth2AuthenticationException이어야 FailureHandler로 흘러간다!
        //     ※ 카카오 일반 앱은 email 동의항목이 없으므로, 실습 중엔 이 검증을 주석 처리
        if (userInfo.email() == null) {
            throw new OAuth2AuthenticationException(
                    new OAuth2Error("email_not_found"),
                    "SNS 계정에서 이메일을 가져오지 못했습니다. 이메일 제공 동의가 필요합니다.");
        }

        // (6) 기존 회원: 프로필 갱신 후 로그인 진행 / 미가입: DB 저장 ★없이★ 미가입 principal 반환
        return userRepository.findByProviderAndProviderId(provider, userInfo.id())
                .map(existing -> {
                    existing.updateProfile(userInfo.name()); // 변경감지로 자동 UPDATE
                    return new CustomOAuth2User(existing, provider, userInfo,
                            oAuth2User.getAttributes(), nameAttributeKey);
                })
                .orElseGet(() -> CustomOAuth2User.unregistered(provider, userInfo,
                        oAuth2User.getAttributes(), nameAttributeKey));
    }
}
```

**`config/oauth/OAuth2SuccessHandler.java`** — 파이프라인의 마지막 훅
```java
// SNS 인증 결과를 "우리 신분증"(자체 JWT)으로 바꿔주는 곳.
// 자체 로그인과 달리 마지막이 ajax가 아니라 "브라우저 리다이렉트"라서 본문으로 토큰을 못 준다.
// → refresh token만 HttpOnly 쿠키로 심고 "/"로 리다이렉트하면,
//   hello.js가 refresh 쿠키로 access token을 받아온다(3번 과제 인프라 재사용, URL 노출 없음).
@Component
@RequiredArgsConstructor
public class OAuth2SuccessHandler extends SimpleUrlAuthenticationSuccessHandler {

    private final TokenService tokenService;
    private final JwtProperties jwtProperties;
    private final TokenProvider tokenProvider; // 미가입자용 "가입 토큰" 발급

    @Override
    public void onAuthenticationSuccess(HttpServletRequest request, HttpServletResponse response,
                                        Authentication authentication) throws IOException {
        CustomOAuth2User principal = (CustomOAuth2User) authentication.getPrincipal();

        String targetUrl;
        if (principal.isRegistered()) {
            // 기존 회원: 자체 로그인과 똑같이 토큰 쌍 발급, refresh는 쿠키로
            TokenService.TokenPair tokens = tokenService.issueTokens(principal.getUser());
            CookieUtil.addCookie(response, CookieUtil.REFRESH_TOKEN_COOKIE, tokens.refreshToken(),
                    (int) jwtProperties.getRefreshTokenValidity().toSeconds());
            targetUrl = "/";
        } else {
            // 미가입: 아직 계정을 만들지 않는다(명시적 가입 정책).
            // SNS 프로필을 담은 10분짜리 "가입 토큰"을 발급해 동의 페이지로 보낸다.
            String signupToken = tokenProvider.createSignupToken(
                    principal.getProvider(), principal.getUserInfo());
            targetUrl = UriComponentsBuilder.fromUriString("/users/oauth-join")
                    .queryParam("signupToken", signupToken)
                    .build().toUriString();
        }

        if (response.isCommitted()) {
            logger.debug("응답이 이미 커밋되어 " + targetUrl + " 로 리다이렉트할 수 없습니다.");
            return;
        }
        getRedirectStrategy().sendRedirect(request, response, targetUrl);
    }
}
```

**`config/oauth/OAuth2FailureHandler.java`**
```java
// 실패 경로: 동의 거부, state 불일치, 토큰 교환 실패, loadUser의 OAuth2AuthenticationException 등.
// 브라우저 "페이지 이동" 중이라 JSON을 줄 JS가 없다 → 리다이렉트 + ?error= 쿼리가 유일한 응답 수단
@Component
public class OAuth2FailureHandler extends SimpleUrlAuthenticationFailureHandler {

    @Override
    public void onAuthenticationFailure(HttpServletRequest request, HttpServletResponse response,
                                        AuthenticationException exception) throws IOException {
        String targetUrl = UriComponentsBuilder.fromUriString("/users/login")
                .queryParam("error", exception.getLocalizedMessage())
                .encode(StandardCharsets.UTF_8)   // 한글 메시지 → 인코딩 필수
                .build().toUriString();

        getRedirectStrategy().sendRedirect(request, response, targetUrl);
    }
}
```

**`config/jwt/TokenProvider.java`** — 가입 토큰 부분 추가
```java
// ---- 가입 토큰(signup token)용 상수 ----
// 같은 서명 키로 만들지만 "용도"가 다르므로 type 클레임으로 구분한다.
// access 토큰을 가입 API에 들이밀어도 type 검사에서 걸러진다
private static final String CLAIM_TYPE = "type";
private static final String TOKEN_TYPE_SIGNUP = "signup";
private static final String CLAIM_PROVIDER = "provider";
private static final String CLAIM_EMAIL = "email";
// 동의 페이지에 머무는 짧은 시간만 유효하면 된다. 길수록 URL로 노출된 토큰의 위험도 커진다
private static final Duration SIGNUP_TOKEN_VALIDITY = Duration.ofMinutes(10);

// [미가입 사용자의 SNS 프로필을 "서버 저장 없이" 가입 페이지까지 운반하는 토큰]
// 아직 User 엔티티가 없으므로 generateToken(User, ...)을 못 쓰고 OAuth2UserInfo에서 직접 채운다.
public String createSignupToken(AuthProvider provider, OAuth2UserInfo userInfo) {
    Date now = new Date();
    return Jwts.builder()
            .header().type("JWT").and()
            .issuer(jwtProperties.getIssuer())
            .issuedAt(now)
            .expiration(new Date(now.getTime() + SIGNUP_TOKEN_VALIDITY.toMillis()))
            .subject(userInfo.id())                    // sub = SNS 회원번호(providerId)
            .claim(CLAIM_TYPE, TOKEN_TYPE_SIGNUP)      // 용도 표식
            .claim(CLAIM_PROVIDER, provider.name())
            .claim(CLAIM_EMAIL, userInfo.email())
            .claim(CLAIM_NAME, userInfo.name())
            .signWith(secretKey, Jwts.SIG.HS512)
            .compact();
}

// 가입 토큰 검증 + 클레임 복원. 셋 중 하나라도 어긋나면 가입 불가:
// ① 서명 위조 ② 10분 만료 ③ 가입 토큰이 아님(type 불일치)
public SignupPayloadDto getSignupPayload(String token) {
    Claims claims;
    try {
        claims = getClaims(token);   // 서명·만료는 파서가 검증(실패 시 예외)
    } catch (Exception e) {
        throw new IllegalArgumentException("유효하지 않거나 만료된 가입 토큰입니다. 소셜 로그인부터 다시 시도해주세요.");
    }

    if (!TOKEN_TYPE_SIGNUP.equals(claims.get(CLAIM_TYPE, String.class))) {
        throw new IllegalArgumentException("가입 토큰이 아닙니다.");
    }

    return new SignupPayloadDto(
            AuthProvider.valueOf(claims.get(CLAIM_PROVIDER, String.class)),
            claims.getSubject(),
            claims.get(CLAIM_EMAIL, String.class),
            claims.get(CLAIM_NAME, String.class)
    );
}
```

```java
    User user = userRepository.findByProviderAndProviderId(payload.getProvider(), payload.getProviderId())

                            .name(payload.getName())
                            .email(payload.getEmail())
                            .provider(payload.getProvider())
                            .providerId(payload.getProviderId())
                            // password는 null — 소셜 회원이 자체 로그인을 시도하면 matches()가 실패해 자연 차단
                            .role(role != null ? role : Role.ROLE_USER)
                            .build()
            ));

    TokenService.TokenPair tokens = tokenService.issueTokens(user);

    return SignInResponseDto.builder()
            .isLoggedIn(true).message("가입이 완료되었습니다.").url("/")
            .accessToken(tokens.accessToken())
            .refreshToken(tokens.refreshToken())
            .userId(user.getUserId()).userName(user.getName())
            .build();
}
```

## 0. 먼저 알아둘 점

- 완성하면 이렇게 동작해요: **"카카오 로그인" 클릭 → 카카오 화면에서 로그인·동의 → (첫 방문) 가입 동의 페이지에서 확정 → 우리 JWT 발급 → 이후는 3번 과제와 완전히 동일한 Bearer 인증.**
- **3번 과제(token) 프로젝트를 기반으로 시작해요.** JWT 인프라 전체(`TokenProvider`, `TokenAuthenticationFilter`, `TokenService`, refresh 재발급, `CookieUtil`, 프론트 JS)를 그대로 재사용해요. 소셜 로그인은 그 위에 "입구 하나"를 얹는 거예요.
- **이번 과제는 코드보다 "누가 무엇을 해주는가"가 어려워요.** 리다이렉트, state 검증, 코드↔토큰 교환, user-info 조회는 전부 프레임워크가 해요. 우리가 만드는 건 파이프라인 양 끝의 훅 두 개 — `loadUser()`(제공자 회원 → 우리 회원 연결)와 `SuccessHandler`(성공 후처리)예요.
- **준비물이 하나 늘어요: 카카오 개발자 콘솔.** [developers.kakao.com](https://developers.kakao.com)에서 앱을 만들고 키를 받아야 해요 (Step 0에서 안내).
- ⚠️ **이 과제 최대의 함정 셋**: ① 콘솔의 Redirect URI와 yaml의 `redirect-uri` 불일치(KOE006), ② `client-authentication-method: client_secret_post` 누락(카카오는 Basic 헤더를 안 받아요), ③ email 동의항목 — 카카오 일반 앱은 email을 못 받아요(비즈 앱 전용). 실습 중엔 email 검증을 조정해요.
- ⚠️ **"URL이 있으면 컨트롤러가 있겠지"라는 감각이 이번엔 안 통해요.** `/oauth2/authorization/kakao`도 `/login/oauth2/code/kakao`도 매핑된 컨트롤러가 없어요 — 필터가 가로채는 규약 경로예요. 이게 이번 과제에서 가장 헷갈리는 지점이에요.
- 카카오가 주는 access token과 우리가 발급하는 JWT는 **완전히 다른 토큰**이에요. 카카오 토큰은 프로필을 한 번 읽는 데 쓰고 버려요. 이후 인증은 전부 우리 JWT — 소셜 로그인이 끝나면 소셜/자체 로그인의 구분 자체가 사라져요.

## 3. 핵심 개념

### (1) OAuth2 — 비밀번호를 넘기지 않고 권한을 위임한다

우리 서비스가 사용자의 카카오 프로필을 쓰려면? **최악의 방법**: 사용자에게 카카오 비밀번호를 받아 우리가 대신 로그인 (절대 금지 — 비밀번호가 제3자에 노출되고, 회수도 범위 제한도 불가능). **OAuth2의 방법**: 사용자가 "카카오에게 직접" 허락하고, 우리는 그 허락의 증표(access token)만 받아요.

등장인물 4명 — 처음에 가장 헷갈리는 게 "Client = 사용자"가 아니라는 점이에요:

| 역할 | 뜻 | 우리 실습에서 |
|------|------|------|
| Resource Owner | 자원의 주인 = 사용자 | 카카오 계정의 주인 |
| **Client** | 자원을 쓰고 싶은 제3자 앱 = **우리 서비스** | 이 프로젝트 |
| Authorization Server | 허락(인가)을 발급하는 서버 | kauth.kakao.com |
| Resource Server | 실제 자원을 보관한 서버 | kapi.kakao.com |

OAuth2 문서의 `client_id`/`client_secret`은 전부 **우리 서비스의 자격증명**이에요.

### (2) 인가 코드 방식 (Authorization Code Grant) — 표준 흐름 6단계

```
1) Client가 사용자를 인가 페이지로 리다이렉트 (client_id, redirect_uri, scope, state)
2) 사용자가 "카카오 화면에서" 로그인 + 동의
3) 카카오가 redirect_uri로 "인가 코드(code)"를 돌려준다 (브라우저 경유)
4) Client 서버가 code + client_secret으로 토큰 엔드포인트에 직접 요청 (브라우저 안 거침)
5) 카카오가 access token 발급
6) Client가 그 토큰으로 Resource Server에서 사용자 정보 조회
```

- **왜 토큰을 바로 안 주고 코드를 거치나?** 1~3은 브라우저를 지나는 **프론트 채널** — URL·히스토리에 남아 탈취 위험이 있어요. 그래서 브라우저에는 1회용 교환권(code)만 흘리고, 진짜 토큰은 4~5의 **백 채널**(서버↔서버 직통)에서만 오가요. 코드를 훔쳐도 client_secret 없이는 토큰으로 못 바꿔요.
- **state**: 1에서 만든 난수가 3에서 그대로 돌아왔는지 대조 — 공격자가 자기 계정의 코드를 피해자에게 심는 CSRF를 막아요. Spring이 자동 생성·검증해요.

### (3) Spring의 oauth2Login() — 프레임워크가 어디까지 해주나

```
GET /oauth2/authorization/kakao        ← 로그인 버튼(단순 <a> 링크)
 → [프레임워크] OAuth2AuthorizationRequestRedirectFilter가 가로챔
   state 생성·보관 + 카카오 인가 페이지로 리다이렉트          (표준 흐름 1)

(카카오 화면에서 로그인·동의 — 우리 서버 무관)                 (표준 흐름 2)

GET /login/oauth2/code/kakao?code=...&state=...
 → [프레임워크] OAuth2LoginAuthenticationFilter가 가로챔     (표준 흐름 3)
   ├─ state 검증
   ├─ code + client_secret → 토큰 교환                      (표준 흐름 4~5)
   ├─ 그 토큰으로 user-info 조회                             (표준 흐름 6)
   ├─ ★ CustomOAuth2UserService.loadUser()   ← 우리 코드의 첫 도착지 (훅 1)
   └─ ★ OAuth2SuccessHandler / FailureHandler ← 우리 코드의 종착점 (훅 2)
```

- 두 URL을 받는 **컨트롤러는 존재하지 않아요.** 요청은 DispatcherServlet에 도달하기 전에 필터가 소비해요. 디버깅할 땐 `loadUser()`에 브레이크포인트 — 콜백 직후 흐름을 잡는 1순위 지점이에요.
- 제공자별 차이(엔드포인트, scope, secret 전달 방식)는 코드가 아니라 **yaml의 registration/provider가 흡수**해요. 그래서 네이버를 추가해도 Java 코드는 거의 안 바뀌어요.
- STATELESS인데 state는 어디에? — 기본 저장소가 세션이에요. STATELESS는 "SecurityContext를 세션에 안 담는다"는 뜻이지 세션 생성 금지가 아니라서, 핸드셰이크 몇 초만 세션이 쓰이고 이후 인증은 여전히 JWT로만 이뤄져요.

### (4) 카카오 토큰 ≠ 우리 JWT — 소셜 로그인은 "입구"만 연다

- OAuth2는 원래 '인가(권한 위임)' 프레임워크예요. "카카오가 프로필을 내줬다" = "카카오에서 인증된 사람이다"라는 점을 로그인에 응용한 게 소셜 로그인이에요 (이 응용을 표준화한 게 OIDC).
- 카카오 access token은 **user-info를 한 번 읽는 데 쓰고 버려요.** 이후 우리 API 인증은 3번 과제의 JWT 체계 그대로 — 권한(Role)·만료 정책을 카카오가 아니라 **우리가** 통제하기 위해서예요.
- 그래서 로그인이 끝나면 소셜/자체 회원의 구분이 사라져요. `TokenAuthenticationFilter`는 어느 입구로 들어왔는지 몰라요.

### (5) 명시적 가입 정책과 "가입 토큰" — 이 과제의 설계 하이라이트

SNS 인증을 통과했다고 곧바로 가입시키지 않아요. 동의 페이지를 보여주고, **동의해야 그때 INSERT**해요. 그럼 "동의 페이지를 보는 동안" SNS 프로필은 어디에 보관하죠?

| 선택지 | 문제 |
|------|------|
| 세션에 임시 저장 | STATELESS 원칙이 깨져요 |
| DB에 임시 행 저장 | 동의 안 하면 "유령 계정"이 남아요 |
| **서명된 10분짜리 JWT에 실어 클라이언트에게** | ✅ 채택 — 서버는 아무것도 기억 안 하고, 서명 덕분에 조작도 불가능해요 |

3번 과제에서 배운 "서명이 곧 신뢰"를 그대로 재활용한 거예요. 같은 서명 키를 쓰되 `type: signup` 클레임으로 용도를 구분해서, 가입 토큰을 API 인증에 쓰거나 access 토큰을 가입에 쓰는 교차 사용을 막아요.

또 하나 — 소셜 회원의 식별 기준은 email이 아니라 **(provider, providerId) 쌍**이에요. 이메일은 동의 여부에 따라 없을 수도, 바뀔 수도 있지만 SNS 회원번호는 불변이니까요. 같은 이메일이라도 제공자가 다르면 별개 계정이에요.

```
[기억법] 컨트롤러 없는 URL 두 개(필터가 가로챔) / 우리 코드는 훅 두 개(loadUser + SuccessHandler)
        / 카카오 토큰은 한 번 쓰고 버림(이후는 우리 JWT) / 식별은 provider+providerId
        / 미가입은 저장 대신 서명된 가입 토큰으로
```

## 5. Step by Step

### Step 0. 프로젝트 준비 — 설정만으로 카카오 화면까지

**목표**: 코드 한 줄 없이 **설정만으로** "카카오 로그인 화면이 뜨는 것"까지 확인해요. 프레임워크가 표준 흐름 1~2를 대신해준다는 걸 몸으로 느끼는 단계예요.

**할 일**
1. 3번 과제 프로젝트를 복사하고, `build.gradle`에 `spring-boot-starter-security-oauth2-client`를 추가해요.
2. 위 "준비물"대로 카카오 콘솔에서 앱을 만들고 키 2개(REST API 키, Client Secret)를 받아요.
3. `application.yaml`에 `spring.security.oauth2.client`의 **registration**(client-id/secret, redirect-uri, grant-type, `client-authentication-method: client_secret_post`, scope)과 **provider**(authorization-uri, token-uri, user-info-uri, `user-name-attribute: id`)를 채워요.
4. 서버를 띄우고 브라우저에서 `http://localhost:8080/oauth2/authorization/kakao` 로 직접 접속해 보세요.

<details>
<summary>💡 힌트 보기</summary>

- registration의 키 이름(`kakao:`)이 곧 **registrationId**가 돼요. 진입 URL(`/oauth2/authorization/kakao`)과 콜백 URL(`/login/oauth2/code/kakao`)의 마지막 조각이 전부 이 이름이에요. 마음대로 바꾸면 콘솔의 Redirect URI와 어긋나요.
- 깃허브 같은 유명 제공자는 Spring이 미리 알아서(`CommonOAuth2Provider`) provider 블록이 필요 없지만, **카카오는 모르는 제공자**라 엔드포인트를 전부 직접 알려줘야 해요.
- `client-authentication-method: client_secret_post` — client_secret을 Basic 헤더로 보낼지 POST 본문으로 보낼지는 제공자마다 달라요. 카카오는 POST 본문만 받아요. 빼면 기본값(Basic)으로 보내다 토큰 교환에서 인증 실패가 나요.
- `user-name-attribute: id` — 응답의 어떤 키가 "사용자 식별자"인지 제공자마다 달라서 알려줘야 해요. **빼면 부팅 시점에 설정 오류로 죽어요**(필수값).
- scope는 **콘솔 동의항목에 설정한 것만** 요청할 수 있어요. 미설정 scope를 요청하면 카카오 인가 페이지에서 KOE 에러가 나요.
- 실무에선 client-id/secret을 커밋하면 안 돼요 — `${KAKAO_CLIENT_ID}` 환경변수 주입이 정석이에요. 실습에선 직접 붙여넣되, 공개 저장소에 올리지 마세요.

</details>

**확인**: `/oauth2/authorization/kakao` 접속 → **카카오 로그인 화면으로 리다이렉트**되면 성공이에요. 이 URL을 받는 컨트롤러를 만든 적이 없다는 걸 다시 확인하세요 — 필터가 가로챈 거예요. (로그인·동의까지 하면 콜백에서 에러가 나요 — `loadUser` 이후가 아직 없으니 정상!)

### Step 1. DB와 엔티티 — 소셜 회원을 수용할 자리 만들기

**목표**: "소셜 회원은 무엇으로 식별하는가"를 스키마에 반영해요 — 답은 **(provider, providerId) 쌍**이에요.

**할 일**
1. `AuthProvider` enum(`LOCAL`, `KAKAO`)을 만들어요. `from(registrationId)` 정적 메서드도 함께.
2. `User` 엔티티에 `provider`(`@Enumerated(STRING)`, `@Builder.Default`로 LOCAL), `providerId` 필드와 `updateProfile(name)` 메서드를 추가해요.
3. DB에 컬럼을 추가해요 (ddl-auto를 안 쓰니 수동):
```sql
ALTER TABLE user ADD COLUMN provider VARCHAR(20) NOT NULL DEFAULT 'LOCAL';
ALTER TABLE user ADD COLUMN provider_id VARCHAR(100) NULL;
```
4. `UserRepository`에 `findByProviderAndProviderId`를 추가해요.

<details>
<summary>💡 힌트 보기</summary>

- **왜 email로 식별하지 않나요?** 이메일은 동의 여부에 따라 아예 없을 수 있고, 사용자가 SNS에서 바꿀 수도 있어요. SNS 회원번호(providerId)는 불변이에요. "같은 이메일 = 같은 사람"이라고 가정하면 제공자가 다른 두 계정이 충돌해요.
- enum 저장은 반드시 `EnumType.STRING` — ORDINAL(0,1,...)로 저장하면 enum 선언 순서만 바뀌어도 기존 데이터의 의미가 깨져요.
- `DEFAULT 'LOCAL'`의 역할은 **기존 행 backfill**이에요(이미 가입한 자체 회원들이 'LOCAL'로 채워짐). 신규 INSERT에는 DB DEFAULT가 적용될 기회가 없어요 — **JPA는 INSERT에 모든 매핑 컬럼을 명시**(null 포함)하니까요. 그래서 신규 행의 기본값은 엔티티의 `@Builder.Default`가 책임져요. 두 겹이 각자 다른 일을 하는 거예요.
- ⚠️ enum에 없는 문자열이 DB에 있으면 그 행을 **읽는 순간** 변환 예외가 터져요. 자체 가입 회원 행 하나 때문에 로그인 전체가 깨질 수 있는 지점 — DEFAULT를 'Local'(소문자)로 넣는 실수 조심.
- `updateProfile`은 setter 대신 **의도가 드러나는 이름**의 메서드로. 영속 상태 엔티티 + 트랜잭션이면 dirty checking으로 자동 UPDATE — `save()` 호출이 필요 없어요(Step 3에서 사용).

</details>

**확인**: 컴파일 + 서버 기동 + 기존 자체 로그인이 여전히 되면 통과예요. DB에서 기존 회원 행의 provider가 'LOCAL'로 채워졌는지도 확인하세요.

### Step 2. 제공자 응답 파싱 계층 — 카카오의 중첩 JSON 길들이기

**목표**: 카카오 응답에서 필요한 값 4개(id/email/name/imageUrl)를 꺼내는 계층을 만들되, **인터페이스로 추상화**해서 새 제공자를 추가해도 상위 코드가 안 바뀌게 해요.

**할 일**
1. `OAuth2UserInfo` 인터페이스: `attributes()`, `id()`, `email()`, `name()`, `imageUrl()`.
2. `KakaoUserInfo`: 카카오 응답 구조에 맞춰 구현해요. 응답은 이렇게 중첩돼 있어요:
```json
{
  "id": 123456789,
  "kakao_account": {
    "email": "user@example.com",
    "profile": { "nickname": "홍길동", "profile_image_url": "https://..." }
  }
}
```
3. `OAuth2UserInfoFactory`: `AuthProvider` → 구현체를 고르는 switch식 팩토리.

<details>
<summary>💡 힌트 보기</summary>

- ⚠️ 카카오는 미동의 항목을 `null`로 주는 게 아니라 **키 자체를 생략**해요. `kakao_account`가 없을 수도, 그 안의 `profile`이 없을 수도 → **모든 중첩 접근에 널 가드**가 필수예요. NPE로 터뜨리는 대신 null을 반환하고, "email 없으면 거부" 같은 **정책 판단은 상위(Step 3)에** 맡기세요 — 이 클래스의 책임은 '값 추출'까지예요.
- `id`는 JSON 숫자(Long)로 와요 → `String.valueOf()`로 문자열화해서 `providerId`(String)에 맞춰요.
- `KakaoUserInfo`는 record로 만들기 딱 좋아요: 상태가 응답 맵 하나뿐인 불변 객체이고, 컴포넌트 이름을 `attributes`로 지으면 인터페이스의 `attributes()`가 자동 구현돼요.
- 팩토리의 switch **식**은 모든 enum 상수를 다루도록 컴파일러가 강제해요(완전성 검사). `LOCAL`엔 예외를 던지는 case를 명시하세요 — 나중에 `NAVER`를 enum에 추가하면 이 switch가 컴파일 에러로 "여기도 고쳐"라고 알려줘요.
- 이 구조의 보상은 Step 3에서 나타나요: `CustomOAuth2UserService`는 `OAuth2UserInfo` 인터페이스만 알아요. 네이버를 추가해도 그 클래스는 한 줄도 안 바뀌어요(개방-폐쇄 원칙).

</details>

**확인**: 컴파일되면 통과예요. "카카오가 nickname 동의를 안 받은 사용자의 응답이 오면 `name()`은 뭘 반환해야 하나?"에 답해 보세요 (null — 그리고 그걸로 뭘 할지는 이 클래스가 결정하지 않아요).

### Step 3. loadUser() — 제공자의 회원을 우리 회원으로 연결한다

**목표**: 파이프라인의 첫 번째 훅. user-info 조회 직후 호출되는 `loadUser()`에서 **기존 회원/미가입을 판별**해요. 미가입이면 DB에 저장하지 **않는** 게 포인트예요(명시적 가입 정책).

**할 일**
1. `CustomOAuth2User implements OAuth2User`: 우리 `User`(미가입이면 null), `AuthProvider`, `OAuth2UserInfo`, 원시 `attributes`, `nameAttributeKey`를 품는 어댑터. `isRegistered()`, 정적 팩토리 `unregistered(...)`, 그리고 계약 메서드 3개(`getAttributes`/`getAuthorities`/`getName`)를 구현해요.
2. `CustomOAuth2UserService extends DefaultOAuth2UserService`, `loadUser()` 오버라이드:
   - `super.loadUser(userRequest)`로 원시 프로필 획득 (딱 한 번만!)
   - registrationId → `AuthProvider`, 원시 맵 → `OAuth2UserInfoFactory.of(...)`
   - email이 null이면 `OAuth2AuthenticationException` (※ 카카오 일반 앱 실습이면 이 검증은 주석 처리)
   - `findByProviderAndProviderId`로 조회 → 기존: `updateProfile` 후 반환 / 미가입: `unregistered` 반환

<details>
<summary>💡 힌트 보기</summary>

- **UserDetailService와의 대구**로 기억하세요:
  - 자체 로그인: `loadUserByUsername(username)` → DB 조회 → `CustomUserDetails` (없으면 예외 = 실패)
  - 소셜 로그인: `loadUser(request)` → DB 조회 → `CustomOAuth2User` (없으면 **미가입 principal**)
- `DefaultOAuth2UserService`를 상속하는 이유: 부모의 `loadUser()`가 "user-info 엔드포인트로 HTTP 요청을 보내는" 코드를 전부 갖고 있어요. `super.loadUser()`로 결과만 받고 우리 도메인 연결만 덧붙여요. ⚠️ **호출할 때마다 실제 HTTP 요청이 나가요** — 반드시 한 번만.
- ⚠️ 예외는 반드시 **`OAuth2AuthenticationException`** — `loadUser()`는 시큐리티 필터 안에서 호출되므로, 이 타입이어야 필터가 "인증 실패"로 인식해 `FailureHandler`(Step 4)로 보내줘요. 다른 RuntimeException은 처리되지 않은 500으로 새어 나가요.
- `getAuthorities()`에서 빈 리스트를 반환하면 "로그인은 됐지만 아무 권한 없는 사용자"가 돼요. 미가입(user == null)은 임시 권한 `ROLE_GUEST`, 기존 회원은 `user.getRole().name()`.
- ⚠️ import 함정: IDE 자동완성이 권하는 `java.security.AuthProvider`는 이름만 같은 암호화(JCA) 클래스예요. 우리 enum의 패키지인지 import를 확인하세요.
- `@Transactional`을 붙이는 이유: `updateProfile()`의 dirty checking이 트랜잭션 안에서 일어나야 UPDATE가 나가요.

</details>

**확인**: 컴파일되면 통과. 흐름으로 답해 보세요 — "미가입 사용자가 카카오 인증을 통과하면 DB에는 무엇이 생기나?" (아무것도 — 그게 명시적 가입 정책이에요.)

### Step 4. 핸들러와 조립 — 성공은 JWT로, 실패는 메시지로

**목표**: 파이프라인의 종착점 두 개를 만들고 `SecurityConfig`에 조립해요. 이 Step이 끝나면 **파이프라인 전체가 한 바퀴** 돌아요 (가입 확정은 다음 Step).

**할 일**
1. `OAuth2FailureHandler extends SimpleUrlAuthenticationFailureHandler`: 실패 사유를 `?error=`에 실어 `/users/login`으로 리다이렉트 (한글이니 UTF-8 인코딩!).
2. `OAuth2SuccessHandler extends SimpleUrlAuthenticationSuccessHandler`:
   - principal을 `CustomOAuth2User`로 캐스팅, `isRegistered()`로 분기
   - **기존 회원**: `tokenService.issueTokens()` → refresh token만 HttpOnly 쿠키에 심고 `"/"`로 리다이렉트
   - **미가입**: 일단 임시로 `/users/login?error=가입 기능은 다음 스텝에서!` 로 리다이렉트 (Step 5에서 교체)
3. `SecurityConfig`: `.oauth2Login(...)`으로 `userService`/`successHandler`/`failureHandler` 3개를 연결해요.
4. `login.html`에 카카오 로그인 버튼(`<a href="/oauth2/authorization/kakao">`)과 `?error=` 표시 스크립트를 추가해요.

<details>
<summary>💡 힌트 보기</summary>

- **왜 access token을 여기서 안 주나?** 자체 로그인은 ajax라 응답 "본문"으로 줄 수 있었지만, OAuth2의 마지막은 **브라우저 리다이렉트**라 본문을 받을 JS가 없어요. 선택지는:
  - URL 쿼리에 토큰 싣기 → URL·히스토리·리퍼러에 노출. 탈락.
  - **refresh token만 HttpOnly 쿠키로 심고 "/"로 보내기** → 채택. "/"의 hello.js는 localStorage에 access가 없으면 refresh 쿠키로 `/api/tokens/refresh`를 호출하잖아요? **3번 과제에서 만든 복구 흐름이 여기서 공짜로 재사용돼요.** 토큰이 URL에 전혀 노출되지 않아요.
- **왜 FailureHandler는 JSON이 아니라 리다이렉트?** 응답을 받는 상대가 달라요. 자체 로그인 실패는 ajax의 error 콜백이 JSON을 파싱하지만, OAuth2 콜백은 브라우저가 주소창째로 이동 중이라 **응답을 파싱할 JS가 어디에도 없어요.** JSON을 주면 사용자 화면에 날 JSON 텍스트가 그대로 찍혀요. 일관성의 기준은 "핸들러끼리"가 아니라 "**클라이언트 유형끼리**"예요: ajax → 상태코드+JSON / 브라우저 이동 → 리다이렉트+쿼리.
- 두 핸들러 모두 시큐리티 필터 안이라 `@ResponseBody` 직렬화를 못 써요. 리다이렉트는 부모가 주는 `getRedirectStrategy().sendRedirect(...)`를 쓰세요 (직접 `response.sendRedirect` 대신 — 컨텍스트 경로 보정 등 스프링의 URL 규칙이 일관 적용돼요).
- `oauth2Login()`의 세 연결 지점: `userInfoEndpoint().userService(...)` = user-info 조회 직후 훅 교체, `successHandler` = 기본 동작(세션 저장 후 원래 페이지로)이 무의미하니 교체, `failureHandler` = 기본 리다이렉트 경로가 폼로그인 기준이라 교체.
- 카카오 버튼은 **ajax가 아니라 단순 링크**예요. 자체 로그인(ajax)과 달리 이후 과정 전체가 "페이지 이동"으로 진행돼요.

</details>

**확인**: ① 카카오 로그인(미가입) → 로그인 페이지에 임시 에러 메시지가 뜨면 파이프라인이 한 바퀴 돈 거예요! ② 카카오 동의 화면에서 "취소" → 로그인 페이지에 실패 메시지. ③ (email 검증을 켰다면) 이메일 미동의 계정 → "이메일 제공 동의가 필요합니다" 메시지. 모두 **우리가 만든 두 훅**을 통과한 결과예요.

### Step 5. 가입 토큰과 동의 페이지 — 미가입 분기 완성

**목표**: 이 과제의 하이라이트예요. 미가입자의 SNS 프로필을 **서버에 저장하지 않고** 동의 페이지까지 운반했다가, 동의 순간 가입 + 즉시 로그인시켜요.

**할 일**
1. `TokenProvider`에 가입 토큰 기능 추가:
   - `createSignupToken(provider, userInfo)`: `type=signup` 클레임 + provider/email/name 클레임, **수명 10분**
   - `getSignupPayload(token)`: 서명·만료 검증 + **type 검증** 후 `SignupPayloadDto`로 복원
2. `SignupPayloadDto`(provider/providerId/email/name, 불변)와 `OAuthSignUpRequestDto`(signupToken + role)를 만들어요.
3. `TokenService.getSignupPayload(...)` 위임 메서드 → `UserService.oauthSignUp(signupToken, role)`: 토큰 복원 → `findByProviderAndProviderId`로 **있으면 그대로, 없으면 저장**(멱등) → `issueTokens()`로 즉시 로그인 응답.
4. `OAuth2SuccessHandler`의 미가입 분기를 진짜로 교체: 가입 토큰 발급 → `/users/oauth-join?signupToken=...` 리다이렉트.
5. 웹 계층: `GET /users/oauth-join`(뷰), `POST /api/users/oauth-join`(가입 확정, 응답 패턴은 자체 로그인과 동일 — access는 본문/refresh는 쿠키), `oauth-join.html` + `oauthJoin.js`(토큰의 payload를 디코딩해 닉네임 표시, 동의 시 토큰+role 제출).
6. `SecurityConfig` permitAll에 `/users/oauth-join`, `/api/users/oauth-join` 추가.

<details>
<summary>💡 힌트 보기</summary>

- **왜 세션도 DB도 아닌 토큰인가** — 핵심 개념 (5)의 표를 다시 보세요. 서명된 단수명 JWT면 서버는 아무것도 기억하지 않고(STATELESS 유지), 클라이언트가 내용을 조작하면 서명 불일치로 들켜요. "서명이 곧 신뢰"의 재활용이에요.
- `type=signup` 클레임이 **토큰 교차 사용**을 막아요: 가입 토큰엔 id/role 클레임이 없어서 API 인증(access 자리)에 쓰면 실패하고, access 토큰엔 type이 없어서 가입 API에 쓰면 type 검사에서 걸려요.
- 가입 토큰이 URL에 노출되는 건 괜찮나? ① 수명 10분 ② 계정 접근 권한이 아니라 "가입 신청 자격"일 뿐 — access token을 URL에 싣는 것과는 위험의 급이 달라요. 그래도 `oauthJoin.js`에서 `history.replaceState`로 주소창에서 지워주세요.
- `oauthSignUp`의 멱등성: 뒤로가기·새로고침으로 같은 토큰이 두 번 제출돼도 `findBy...().orElseGet(저장)` 구조라 중복 가입이 안 생겨요. (이미 가입된 경우 요청의 role은 무시 — 재가입 시도로 권한을 바꿀 수는 없어야죠.)
- 소셜 회원의 `userId`는 `"kakao_" + providerId`로 생성해요 — 기존 코드가 userId 기반으로 동작하니 유니크한 파생값을 만들어주는 거예요. `password`는 null — 소셜 회원이 자체 로그인 폼으로 시도하면 `matches()`가 실패해 자연 차단돼요.
- 이름/이메일을 **본문으로 받지 않는** 이유: 화면의 값은 표시용일 뿐, 서버는 서명된 토큰에서 직접 꺼내요. 클라이언트가 보내게 하면 조작이 가능해져요. role만 본문으로 — SNS가 주는 정보가 아니라 사용자의 "선택"이니까요.
- `/api/users/oauth-join`이 permitAll인 게 불안한가요? 인증을 Bearer 헤더 대신 **본문의 가입 토큰 검증**이 대신해요. 서명 없이는 통과할 수 없어요.
- 프론트에서 JWT payload 디코딩: `atob`는 Base64Url을 몰라요 → `-`→`+`, `_`→`/` 치환 후 디코딩. 한글 닉네임은 `TextDecoder`로 UTF-8 복원. "브라우저에서도 열린다 = 암호화가 아니라 인코딩"을 눈으로 확인하는 학습 포인트예요.

</details>

**확인**: 전체 시나리오를 돌려요 — ① 카카오 로그인(첫 방문) → 동의 페이지에 **내 카카오 닉네임**이 표시됨 → "동의하고 가입" → 메인에서 "OO님" ② DB에 `kakao_...` 회원 행 생성(password NULL, provider KAKAO) ③ 로그아웃 후 다시 카카오 로그인 → **동의 페이지 없이** 곧바로 메인(기존 회원 분기) ④ 동의 페이지에서 10분 넘게 있다가 제출 → "만료" 안내와 함께 로그인 페이지로.

| 증상 | 원인 / 해결 |
|------|------|
| 카카오 화면에서 **KOE006** | 콘솔의 Redirect URI와 요청의 redirect_uri 불일치. `http://localhost:8080/login/oauth2/code/kakao` — 포트·경로까지 완전히 일치해야. |
| **KOE101** / invalid client | client-id가 REST API 키가 아니에요 (JavaScript 키 등 다른 키를 붙여넣는 실수). |
| 카카오 로그인·동의까지 됐는데 콜백에서 `[invalid_client]` 또는 401 | `client-authentication-method: client_secret_post` 누락 — 카카오는 Basic 헤더를 안 받아요. 또는 콘솔에서 Client Secret "사용함"을 안 켰어요. |
| 서버가 뜨자마자 설정 오류로 죽음 | provider 블록의 `user-name-attribute` 누락(필수값). 또는 yaml 들여쓰기 오류 — registration/provider는 `spring.security.oauth2.client` 아래 형제예요. |
| `/oauth2/authorization/kakao`가 404 | oauth2-client 의존성 누락, 또는 `.oauth2Login()`을 SecurityConfig에 아예 안 붙임 (이 설정이 있어야 필터 두 개가 체인에 등록돼요). |
| 카카오 로그인이 **항상** "이메일을 가져오지 못했습니다"로 실패 | email 검증은 있는데 scope에 email이 없어요. 카카오 일반 앱은 `account_email` 동의항목 자체가 불가(비즈 앱 전용) → 실습 중엔 email 검증을 주석 처리. |
| `loadUser`에서 예외를 던졌는데 FailureHandler로 안 가고 500 | `OAuth2AuthenticationException`이 아닌 예외를 던졌어요. 필터는 이 타입만 "인증 실패"로 인식해요. |
| `AuthProvider`가 이상하게 동작 / 컴파일 에러 | `java.security.AuthProvider`를 import했어요 — 이름만 같은 JCA 클래스. 우리 enum의 import인지 확인. |
| 미가입자가 동의 페이지 대신 `/access-denied`로 감 | `/users/oauth-join`(페이지)나 `/api/users/oauth-join`(API)이 permitAll에 없어요 — 아직 회원이 아닌 사람이 가는 경로예요. |
| 가입 버튼 누르면 400 "가입 토큰이 아닙니다" | signupToken 자리에 access token을 보내고 있어요(localStorage에서 꺼내는 실수). URL 쿼리의 signupToken을 보내야 해요. |
| 가입 버튼 누르면 400 "유효하지 않거나 만료된" | 동의 페이지에서 10분 초과, 또는 토큰을 잘라먹고 전달(URL 인코딩 문제). 소셜 로그인부터 다시. |
| 재로그인해도 카카오 닉네임 변경이 DB에 반영 안 됨 | `loadUser`에 `@Transactional`이 없어요 — dirty checking은 트랜잭션 안에서만 UPDATE를 만들어요. |
| 기존 자체 가입 회원이 로그인하는 순간 enum 변환 예외 | provider 컬럼을 NULL/이상한 문자열로 추가했어요. `UPDATE user SET provider='LOCAL' WHERE provider IS NULL;` — enum에 없는 문자열이 DB에 있으면 읽는 순간 터져요. |
| 새 소셜 회원의 provider가 DB에서 NULL | DB DEFAULT에 기댔어요 — JPA는 INSERT에 모든 컬럼을 명시하므로 DB DEFAULT가 적용될 기회가 없어요. 엔티티 `@Builder.Default` + 가입 코드에서 명시적으로 채우기. |
| 소셜 로그인 성공했는데 메인에서 "로그인이 필요합니다" | SuccessHandler가 refresh 쿠키를 안 심었거나 쿠키 경로/수명이 잘못됐어요. 개발자도구 > Application > Cookies에서 refreshToken 확인. hello.js의 복구 흐름은 refresh 쿠키가 전제예요. |
| 같은 사람인데 로그인할 때마다 새 회원이 생김 | `findByProviderAndProviderId` 조회 키가 잘못됐어요(예: providerId에 닉네임을 저장). providerId는 카카오 회원번호(불변)여야 해요. |

## 6. 학습 체크

- [ ] OAuth2 등장인물 4명을 우리 실습의 실체(우리 서비스/kauth/kapi)와 짝지을 수 있다
- [ ] 인가 코드 방식에서 왜 토큰을 바로 안 주고 code를 거치는지(프론트 채널 vs 백 채널) 설명할 수 있다
- [ ] state 파라미터가 막는 공격과 검증 주체(프레임워크)를 안다
- [ ] `/oauth2/authorization/kakao`와 `/login/oauth2/code/kakao`에 컨트롤러가 없는 이유를 설명할 수 있다
- [ ] 개발자가 구현하는 훅 두 개(loadUser, SuccessHandler)의 위치와 역할을 안다
- [ ] 카카오 access token과 우리 JWT의 용도 차이 — 왜 우리 토큰을 새로 발급하는지 설명할 수 있다
- [ ] 소셜 회원의 식별 기준이 email이 아니라 (provider, providerId)인 이유를 안다
- [ ] 명시적 가입 정책에서 "동의 전 프로필 보관" 문제의 세 가지 선택지와 가입 토큰을 채택한 이유를 설명할 수 있다
- [ ] 가입 토큰의 type 클레임이 막는 것(토큰 교차 사용)을 안다
- [ ] OAuth2 실패 응답이 JSON이 아니라 리다이렉트인 이유(클라이언트 유형)를 설명할 수 있다
- [ ] SuccessHandler가 access token을 직접 안 주고 refresh 쿠키만 심는 전달 전략과 그 이유(URL 노출)를 안다
- [ ] STATELESS 설정과 OAuth2 핸드셰이크의 세션 사용이 왜 모순이 아닌지 설명할 수 있다
- [ ] 새 제공자(네이버)를 추가할 때 바뀌는 것과 안 바뀌는 것을 구분할 수 있다

## 7. 최종 완성 체크리스트

- [ ] 카카오 로그인 버튼 → 카카오 인증 → (첫 방문) 동의 페이지에 내 닉네임이 표시된다
- [ ] "동의하고 가입" → 즉시 로그인 상태로 메인 도착, DB에 provider=KAKAO / password=NULL 행이 생겼다
- [ ] 재로그인 시 동의 페이지 없이 곧바로 로그인된다 (기존 회원 분기)
- [ ] 새로고침으로 가입 요청이 중복돼도 회원이 두 번 생기지 않는다 (멱등)
- [ ] 카카오 동의 화면에서 "취소"하면 우리 로그인 페이지에 실패 메시지가 표시된다
- [ ] 가입 토큰 payload를 조작해 제출하면 서버가 거부한다 (서명 검증 확인)
- [ ] 소셜 계정으로 3번 과제의 모든 API(info/user/admin/refresh/logout)가 자체 계정과 동일하게 동작한다
- [ ] 소셜 회원의 userId로 자체 로그인 폼에서 로그인이 안 된다 (password null)
- [ ] 기존 자체 가입 회원의 로그인이 여전히 잘 된다 (provider='LOCAL' backfill 확인)
- [ ] client-id/client-secret을 공개 저장소에 올리지 않았다 (실무라면 환경변수로)
